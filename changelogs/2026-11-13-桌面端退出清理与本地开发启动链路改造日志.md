# 2026-11-13 桌面端退出清理与本地开发启动链路改造日志

## 1. 改造背景

本轮排查源于两个互相独立的运行期问题：

1. **开发期 CPU 持续高占用**：Vite dev server 单核占用接近 300%，原因是默认文件监视覆盖了 `target/`（4.28 GB、8355 个文件）。
2. **应用关闭即 panic**：每次关闭窗口，Rust 主进程都会在 `RunEvent::Exit` 回调中 panic，ACP 子进程清理逻辑被整段跳过；表现为「关闭应用后可能残留子进程」。

此外，多轮启动过程中反复出现「应用启动后随即消失」，最终定位为**本地启动链路的包装层与端口漂移问题**（非项目代码缺陷，但会稳定复现，故一并记录）。

## 2. 改动点与实现

### 2.1 `perf(dev)`：Vite 监视忽略 Rust 构建产物与打包产物（提交 `a3d6ee3`）

`vite.config.ts` 的 `server` 配置新增：

```ts
watch:
  process.env.DISABLE_HMR === 'true'
    ? null
    : { ignored: ['**/target/**', '**/dist/**', '**/.git/**', '**/*.log'] },
```

- 仅在启用 HMR 时注册 watch 配置，`DISABLE_HMR=true` 时保持关闭，避免临时禁用 HMR 的调试场景反向引入监视开销。
- 生效后实测：监视句柄 9,959 → 741，内存 680 MB → 126 MB，稳态 CPU 从约 315%（单核占比）降至 ≤0.5%。

### 2.2 `fix(tauri-runtime)`：退出清理改为独立线程 runtime（提交 `e25d712`）

`src-tauri/src/main.rs` 的 `RunEvent::Exit` 分支原实现：

```rust
let manager = app_handle.state::<AppState>().acp_manager.clone();
tauri::async_runtime::block_on(async move {
    let mut guard = manager.lock().await;
    if let Err(e) = guard.stop_all().await { /* warn */ }
});
```

`RunEvent::Exit` 回调本身运行在 Tauri 异步运行时上下文中，回调内直接 `block_on` 会触发：

```
thread 'main' panicked at tokio-1.53.1/.../multi_thread/mod.rs:91:9:
Cannot start a runtime from within a runtime.
```

现改为在独立 `std::thread` 中构建专用 `tokio::runtime::Runtime` 执行并 `join`：

```rust
let cleanup = std::thread::spawn(move || {
    let runtime = match tokio::runtime::Runtime::new() {
        Ok(runtime) => runtime,
        Err(e) => { tracing::warn!("Failed to build exit cleanup runtime: {}", e); return; }
    };
    runtime.block_on(async move {
        let mut guard = manager.lock().await;
        if let Err(e) = guard.stop_all().await {
            tracing::warn!("Failed to stop all ACP agents on exit: {}", e);
        }
    });
});
if let Err(e) = cleanup.join() {
    tracing::warn!("Exit cleanup thread panicked: {:?}", e);
}
```

设计要求：

- 独立线程不处于运行时上下文，`Runtime::new()` + `block_on` 合法；
- `join()` 保证主进程在真正退出前完成 `stop_all`，不放宽原有清理时序；
- runtime 构建失败仅告警，不阻断退出。

### 2.3 本地启动链路的运行期结论（非代码改动，写入运维记录）

排查中发现并已确认以下环境行为：

1. **应用数据目录必须显式指定**：应用默认解析到 `C:\Users\<user>\.shadow-crew`（空库，会 fallback 到 in-memory）；本项目本地真实数据位于 `target\shadow-crew-home\.shadow-crew\`。启动前需设置 `SHADOW_CREW_HOME=D:\goProject\src\shadow-crew\target\shadow-crew-home`。
2. **npm/npx 包装层无法稳定持有长驻子进程**：`npm run dev:desktop`、`npm run dev`、`npx tauri dev` 均出现过包装层以 `1 / 127 / 255` 退出、而子进程（Vite、tauri CLI）继续以孤儿进程存活的半死状态。
3. **端口漂移引发连锁失败**：孤儿 Vite 继续占用 3033，下一次启动的 Vite 自动漂移到 3034，而 `src-tauri/tauri.conf.json` 中 `devUrl` 固定为 `http://localhost:3033`，形成启动即失败的表象。
4. **等价可靠启动方式**：先运行 `node node_modules/vite/bin/vite.js --port=3033 --host=0.0.0.0`，再直接运行 `target/debug/shadow-crew-desktop.exe`（带 `SHADOW_CREW_HOME`）。

- **未执行 `cargo test` 全量回归**：本次改动仅涉及 `main.rs` 退出回调，无可测单元；Windows 下既有环境性失败（`test_execute_timeout` 依赖 Git Bash `sleep`、ACP 敏感路径断言使用 POSIX 分隔符）未重新跑通。

- **退出时仍观察到一次遗留进程树**：窗口关闭后仍有一个 `shadow-crew-desktop.exe` 及其 6 个子进程存活，需人工终止；根因未定位，未在本次改动范围内修复。
- **npm/npx 包装层退出的根因未定位**：仅确认「包装层退出、子进程存活」的现象与端口漂移的连锁关系，未深入到 npm 版本或 Windows 控制台信号处理层。
