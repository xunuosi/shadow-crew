# 2026-11-10 运行时预算与循环收敛改造日志

## 1. 改造背景

给 Agent 配置完身份后，简单问题修复或问答仍会出现：

- 多个 Agent 反复接力、互相 `@`，协同链过长；
- 输出内容铺垫多、篇幅长，简单问题回答成本高；
- 阶段契约校验失败后连续 Self-Refine，形成“纠错—再纠错”循环；
- 流式输出逐 token 触发全量前端刷新，并频繁写 SQLite；
- 同一 Agent 在多个房间的流式片段可能串流到其他房间的 pending 卡片。

本次改造目标：把 Token 消耗、协同轮次、自我纠错次数、接力行为变成**每个 Agent 可配置、宿主强制收敛**的运行时策略，并修复流式路由与持久化开销问题。

## 2. 功能点与实现

### 2.1 新增每 Agent 运行时策略

新增 `src/services/agentRuntimePolicy.ts`，定义并集中归一化 `AgentRuntimePolicy`：

| 字段 | 含义 | 默认值 / 边界 |
| --- | --- | --- |
| `maxOutputTokens` | 单轮输出 Token 上限 | `0` 表示不限制，最大 `32768` |
| `cascadeMaxHops` | 该 Agent 参与协同的最大轮次 | `1 ~ 12`，默认 `12` |
| `maxCorrectionRetries` | Stage Contract Self-Refine 次数 | `0 ~ 2`，默认 `2` |
| `autoRelay` | 是否允许主动 `@` 其他 Agent 接力 | 默认 `true` |
| `conciseReplies` | 简洁回答模式 | 默认 `false` |
| `streamFlushIntervalMs` | 前端流式合并刷新间隔 | `0 ~ 500ms`，默认 `40ms` |

同时提供：

- `resolveEffectiveRuntimePolicy`：读取有效策略；
- `resolveCascadeMaxHops`：房间协同轮次取参与 Agent 的最小值；
- `resolveCorrectionRetryLimit`：读取单 Agent 纠错上限；
- `buildRuntimePolicyDirective`：把预算与收敛约束注入系统人设。

### 2.2 策略配置 UI

`src/components/ConnectAgentModal.tsx` 新增「运行时预算与循环收敛 (Runtime Budget)」面板：

- 可调输出上限、协同轮次、自我纠错次数、流式刷新间隔；
- 可开关「简洁回答模式」与「允许主动 @ 接力」；
- 提供「轻量问答预设」：1200 tokens、2 跳、0 次纠错、简洁模式、关闭接力；
- 创建与编辑 Agent 时都会写入 `runtimePolicy`。

### 2.3 旧数据迁移

`src/services/agentMemory.ts` 在 Agent 水合入口 `normalizeHydratedAgent` 中显式迁移：

- 缺失或越界的 `runtimePolicy` 一次性归一化为规范默认值；
- 通过 `isSameAgentRuntimePolicy` 判断是否需要回写，避免隐式兼容散落到业务层。

### 2.4 宿主侧强制收敛

`src/services/agentCollaboration.ts` 与 `src/App.tsx`：

- 系统人设始终注入「收敛约束」：没有新增事实/改动/风险时不得为接话而点名；
- 协同链 `maxDepth` 不再硬编码 12，改为参与 Agent 配置的最小值；
- `checkLoopGuard` 增加目标 Agent 的轮次预算判断，超限时静默收敛；
- Turn Barrier 聚合 `@mention` 时，`autoRelay=false` 的 Agent 不产生下一跳，排队协作者也不会被拉起；
- 三处 Stage Contract Self-Refine 使用各 Agent 的 `maxCorrectionRetries`，为 `0` 时直接熔断转人工；
- 模型调用 `resolveAgentModelConfig` 按 Agent 的 `maxOutputTokens` 裁剪 `maxTokens`。

### 2.5 流式路由与渲染节流

- Rust `src-tauri/src/acp_manager.rs` 在 `acp:chunk` 与 `acp:thinking_heartbeat` 载荷中回填 `session_key`；
- `src/App.tsx` 用 `parseSessionKey(...).roomId` 精确路由到所属房间，避免同一 Agent 跨房间串流；
- 流式片段按房间 + Agent 缓冲，并按 `streamFlushIntervalMs` 合并刷新；
- 同一 Agent 有多个 pending 卡时，始终追加到最新一张。

### 2.6 持久化与启动安全

`src/App.tsx` 消息持久化 Effect：

- 启动水合完成前（`isWorkspaceHydratedRef` 为 `false`）不写库，避免用未加载完的内存快照覆盖历史；
- 写入增加 600ms 防抖，避免每个流式 token 都执行一次全量 SQLite 事务。

### 2.7 HTTP 安全加固

- `src-tauri/src/main.rs` 移除 `native_http_post` 的无条件 `curl -k`，默认校验 TLS；
- 企业内网自签证书需显式设置 `SHADOW_CREW_NATIVE_HTTP_INSECURE_TLS=1`；
- 删除硬编码 `127.0.0.1:7897` 代理回退，仅使用显式环境变量代理；
- `native_http_post` 与 `requestJsonUniversal` 的成功判定改为以 HTTP 状态码为准，不再从响应文本猜 `choices/id/data`。

## 5. 未验证边界与注意事项

- 当前开发环境没有 `cargo`，Rust 侧改动未编译验证，需在有 Rust 工具链的机器执行 `cargo check -p shadow-crew-desktop` 或 `npm run dev:desktop`；
- 未启动真实 Tauri 桌面端与真实 ACP 端点，UI 双主题与真实流式链路未做运行期截图验证；
- TLS 默认收紧后，依赖自签证书的内网网关需设置 `SHADOW_CREW_NATIVE_HTTP_INSECURE_TLS=1`，否则连接会失败；
- 协同轮次取参与者最小值意味着：房间内任一 Agent 配置较小轮次，会约束整个房间的协同链长度，这是刻意设计。
