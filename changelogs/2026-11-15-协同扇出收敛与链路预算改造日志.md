# 2026-11-15 协同扇出收敛与链路预算改造日志

## 1. 改造背景

2026-11-10 的运行时预算改造解决了「单 Agent 可配置」，但在多 Agent 实测中仍暴露五类结构性浪费：

- 用户不 `@` 任何人时，频道内全员被唤醒，一句「好的」也会触发 N 倍模型调用；
- 跳数内没有总量闸门：深度预算只限「轮」，每轮可并发多人，实际 Token 消耗无上界；
- 个别 Agent 卡死后 Turn Barrier 永久停在「推演中」，前端没有任何超时告知，用户只能干等；
- Rust 侧指令串行锁无排队上限、默认空闲 600s / 硬上限 1800s，一次卡死等于 10~30 分钟无效等待，且会话清理任务会无限期挂在同一把锁上；
- 每一跳都把整段历史与全量长文重发给所有参与者，70% 水位与 512K 稳态预算在 1M~2M 窗口模型上线性放大输入成本。

本次改造目标：把「唤醒谁、发多少、等多久、花多少」全部收敛为宿主强制执行的硬约束，并让每一条收敛都具备用户可见的解释。

## 2. 功能点与实现

### 2.1 未点名扇出按相关性收敛

`src/services/agentCollaboration.ts` 新增：

| 符号 | 作用 |
| --- | --- |
| `DEFAULT_MAX_UNMENTIONED_RESPONDERS = 3` | 未点名时单轮最多唤醒的 Agent 数 |
| `resolveMaxUnmentionedResponders()` | 读取 `VITE_MAX_UNMENTIONED_RESPONDERS`，下限 `1` |
| `isTrivialSocialTurn(content)` | 识别极短确认/寒暄，收敛到单一成员 |
| `selectRespondersForUnmentionedTurn(options)` | 未点名时的响应者启发式选择 |
| `tokenizeForRelevance(content)` | 零依赖相关性切分（中文二元组 + 英文/数字词） |

选择策略分三层：

1. **寒暄降级**：正文去空白后 ≤ 12 字且命中「好/好的/收到/谢谢/嗯/继续/go/yes…」词表时，只唤醒最近活跃的一位。空正文刻意**不**判定为寒暄——那通常是「只发附件/图片」，需要多角色视角，收敛到单人反而漏判断；
2. **小群保持自然**：候选数不超过上限时全量参与，不改变小频道的讨论体验；
3. **超限打分收敛**：按「名称/角色/描述关键词命中 +3」「最近活跃首位 +3、其余按位次递减」排序取前 N，并把最近活跃成员确保保留在结果内，避免相关性打分把正在接力的人挤掉。

`src/App.tsx` 中两处「未点名扇出」（标准讨论模式、线程讨论模式）由原来的全员遍历改为调用该函数。

### 2.2 Turn Barrier 硬超时与执行态回收

新增 `settleWithDeadline<T>(tasks, timeoutMs)`：

- 实现方式为 `Promise.race` + `finally` 一次性标记，任务在时限内真正结束时不误记超时；
- 返回 `DeadlineSettleResult`：`{ results, timedOut, timedOutIndexes }`，其中 `timedOutIndexes` 用于让调用方回收对应 Agent 的执行态；
- 默认 `DEFAULT_TURN_BARRIER_TIMEOUT_MS = 300_000`，可通过 `VITE_TURN_BARRIER_TIMEOUT_MS` 覆盖，下限 `5s`。

300s 的取值依据：兜住「卡死」而不是误伤「慢」——单 Agent 复杂推演常需 2~4 分钟；同时它显著小于 Rust 侧 900s 单轮硬上限，两层阈值叠加后最坏等待仍可控。

`src/App.tsx` 新增 `pushBarrierTimeoutNotice(roomId, channelId, timedOut, timedOutAgentIds)`：

- 先按 `timedOutAgentIds` 删除 `${roomId}:${agentId}` 执行态，必要时复位 `isGenerating`，解决「界面永远停在推演中、直到 Rust 侧 900s 上限才结束」的观感来源；
- 再写一条系统卡片（`Barrier Timeout`）说明收敛原因与续跑方式，按 `roomId` 做 60s 节流，避免同一房间连续超时刷屏。

接入点三处：hop 汇合、标准讨论模式 Turn Barrier、线程讨论 Turn Barrier。此外 hop 汇合超时后置位 `hopBarrierClosed`，屏蔽迟到回复继续触发下游跳数。

### 2.3 链路级总预算

新增 `CollaborationCascadeBudget`（`maxModelCalls / usedModelCalls / maxPromptChars / usedPromptChars`），`CollaborationCascade` 增加可选 `budget` 字段：

```ts
createCascadeBudget(agentCount, maxDepth)
  maxModelCalls   = clamp(participants × min(maxDepth, 8), 8, 40)
  maxPromptChars  = clamp(participants × 80_000, 240_000, 960_000)
```

| 参与规模 | 调用额度 | 字符额度 |
| --- | --- | --- |
| 2 人 | 16 次 | 240k |
| 4 人 | 32 次 | 320k |
| 5 人及以上 | 40 次（顶格封顶） | 400k~960k |

`consumeCascadeBudget(cascade, modelCalls, promptChars)` 在 `src/App.tsx` 三处派发前调用（标准讨论、线程讨论、hop 派发），记账「1 次模型调用 + 本次提示词字符数」。该函数刻意容忍 `cascade` 为空：级联可能在派发途中被终止或重建，记账不能反过来把整条链路抛成 `TypeError`。

`checkLoopGuard` 增加预算分支：与深度/频次兜底不同，**预算耗尽属于用户可感知的资源限制**，因此 `isSilentEnd = false`，并显式说明「已达到模型调用预算上限（N 次）/ 上下文投递量上限（Nk 字符），已按当前结论收敛；如需继续，请直接 @ 目标 Agent 追加一轮」，避免看起来像讨论莫名停住。

### 2.4 增量批次与长文本折叠

- `MAX_DELTA_BATCH_EVENTS = 24`：热会话只投递水位线之后最近 24 条增量（约一屏协同对话），`extractUnreadDeltaMessages` 同时回报 `droppedCount`。原 50 条在 4 Agent 频道场景下等价于 200 份长文输入；
- `MAX_DELTA_ENTRY_CHARS = 1200` + `foldLongTextForPrompt(text, maxChars)`：保留首 60% 与尾部，中段以「此处折叠 N 字」占位；当正文含代码块 / 补丁 / 堆栈（三反引号、`+++ `、`--- `）时上限自动抬到 4000，避免把结论载体折叠掉；
- `escapeSemanticText` / `wrapSemanticSection`：非受信正文转义 `& < >`，`<delta-events>`、`<topic-context>` 等语义段显式成对包裹并转义属性值，防止消息正文中的闭合标签破坏提示词语义边界（对标 Buzz `prompt_framing.rs` 的 `escape_semantic_text` / `semantic_section_with_attributes`）。单条增量在序列化前统一走 `foldLongTextForPrompt(escapeSemanticText(content))`。

### 2.5 Rust 侧排队上限与超时基线

`src-tauri/src/acp_manager.rs`：

- 新增 `acquire_prompt_lock_with(wait_secs, label)`：用 `tokio::time::timeout` 包住 `prompt_lock.lock()`，超时返回可读错误（含等待秒数与「稍后重试或终止当前推演」的处置建议）；
- `acquire_prompt_lock`：默认 `120s`，可由 `SHADOW_CREW_ACP_LOCK_WAIT_TIMEOUT` 覆盖，下限 `5s`；`ensure_session` 与指令主路径改用该锁，不再无条件阻塞；
- `clear_sessions_with_generation`：改用 60s 独立等待，失败时打印「跳过本次会话清理」并直接返回，避免同一 Agent 长任务期间清理任务无限挂锁、幽灵任务越积越多；
- 默认超时收敛：空闲 `600s → 180s`、单轮硬上限 `1800s → 900s`、授权等待 `600s → 300s`。三者仍分别可由 `SHADOW_CREW_ACP_IDLE_TIMEOUT` / `SHADOW_CREW_ACP_MAX_DURATION` / `SHADOW_CREW_ACP_PERMISSION_TIMEOUT` 放大，长推演场景不受损。

### 2.6 前端 ACP 客户端口径对齐

`src/services/acpClient.ts`：`IDLE_TIMEOUT_MS 300_000 → 180_000`、`MAX_DURATION_MS 1_800_000 → 900_000`。两端不一致时，前端会继续等一个后端早已判死的请求，属纯浪费。

### 2.7 历史上下文预算与裁剪

`src/services/llmService.ts`：

- 历史安全水位 `0.7 → 0.6`：多 Agent 每一跳都要重发历史，水位越高首字延迟与输入 Token 越线性放大，缺口由既有摘要与折叠机制承接；
- `MAX_DESKTOP_STEADY_BUDGET 512_000 → 192_000`：超大窗口场景优先走摘要压缩而非整段回放；
- 终极安全钳制由「逐字符裁剪」改为「按缺口比例一次砍到位」：`cutChars = ceil(excess / targetTokens × len)`，并加 `clampRounds < 16` 迭代上限兜住「估算取整导致不收敛」的极端情况，消除长会话下 `O(字符数 × 消息数)` 的无效循环。

### 2.8 渲染与进场动画

- `src/components/ChatTimeline.tsx`：消息数变化后的滚动补偿由 `40 / 120 / 250ms` 三次 `setTimeout` 收敛为 `rAF + 120ms` 单次，减少长会话切换时的重复同步布局；
- `src/index.css`：新增约 70 行进场动画兼容层，补齐 `animate-in` / `fade-in` / `zoom-in-95` / `slide-in-from-*` 的原生 keyframes，并遵循 `prefers-reduced-motion`。

### 2.9 测试脚本与阈值解耦

- `test-llm-compaction-governance.ts`：GLM-5.3 / Kimi K3 的 `historyTokenBudget` 断言由 `512000` 改为 `192000`；
- `test-normal-mode-buzz-orchestration.ts`：去掉与硬编码序号绑定的断言，避免批次上限调整后误报。

## 6. 未验证边界与注意事项

- 未编译：`acp_manager.rs` 的 `acquire_prompt_lock_with` 涉及 `tokio::time::timeout` 与 `MutexGuard` 生命周期，虽已复核但必须由 `cargo check` 确认；
- 未跑协同链路测试：`settleWithDeadline` 的 `timedOutIndexes` 下标与调用方 `tasks` 数组顺序强耦合，若后续调整入参数组构造方式需同步回归；
- 预算封顶后行为**显式可见**（系统卡片告知 + 提示 @ 追加），与深度兜底的静默收敛刻意区分，若产品希望静默需改 `isSilentEnd`；
- 300s Turn Barrier 对「慢但正常」的长任务可能提前收敛，届时只会丢弃超时成员、保留其余结论，可通过 `VITE_TURN_BARRIER_TIMEOUT_MS` 放宽；
- Rust 侧 180s 空闲判死对低频心跳的自定义 Agent 偏紧，长思考且不上报心跳的实现需调 `SHADOW_CREW_ACP_IDLE_TIMEOUT`；
- 192K 稳态预算会让超长会话更早触发摘要压缩，历史细节召回率相对下降，需结合摘要质量观察。
