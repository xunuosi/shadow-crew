## 0. 一句话主张

> **Shinobi 不提效于"单位时间产出更多"，而提效于"把人从关键路径上摘下来"——让人不在场时，任务仍然推进。**

这个区别不是修辞。它决定了投入方向、度量口径，以及哪些场景**不应该**交给 Agent。

---

## 1. 为什么必须重新定义"提效"

常见的提效叙事是「AI 让一个人的产出等于三个人」。这个说法在本团队的工程现实里不成立，原因是瓶颈的位置已经变了。

**提效的第一性来源有两个，都是线性以外的收益：**

| 杠杆 | 机制 | 前提条件 |
|---|---|---|
| **无监督推进时长** | 人下线，任务不下线。把研发中的串行等待（等评审、等环境、等队友答复）改为后台并行推进 | ⚠️ **产出必须可机器验证**，否则只是把积压生产得更快 |
| **并行轨道数** | 同一需求的多条技术路线并行出 POC 与取舍证据，人只做收敛决策 | ⚠️ 受人的**上下文带宽**硬约束 |

**关键推论——瓶颈已经迁移：**

```
旧瓶颈：人的产出速率        →  新瓶颈：人的"审阅 + 拍板"带宽
```

Agent 侧产出扩大 N 倍，而决策带宽不变，**净效果是待办积压，不是提效**。因此：

- ❌ 错误度量：单位时间产量（会奖励积压）
- ✅ 正确度量：**决策延迟、人工介入率、返工率**（衡量人是否真的被摘出关键路径）

这一条是整个方案的基石。任何不提"人的带宽"的提效方案，都会在执行层失效。

### 2.4 关于度量数据的一个实测警示 `[已实现]` + `[待验证]`

我们对 `messages` 表（91 行真实数据）做了时间列可用性核查，结论是**三个时间列中两个是陷阱**：

| 列 | 实际语义 | 可用性 |
|---|---|---|
| `id` 内嵌 epoch | 真实事件时间 | ✅ **唯一权威源**（已由两独立来源互证 91/91） |
| `timestamp` | 本地时间**显示字符串**，无日期（如 `"02:25 PM"`） | ⚠️ 仅可作校验，不可作数据 |
| `created_at` | 入库时刻——**91 行中 72 行同为一次批量回放的同一瞬间** | ❌ **禁用**：用它算时间差会得 0，且不报错 |

**这一条必须写进文档**，因为它正是最容易被误当成结论的错误类型。任何在立项阶段引用"现有数据可支撑度量"的承诺，都必须先排除此项。

## 3. 分场景可替代性：决定"能替换什么"的唯一变量是验证成本

对「替换开发人员参与方案讨论、技术排期评估、技术支持」这一目标，三个场景的可行性差一个数量级。判据不是难度，而是：

> **可替代度 ≈ 1 / 人工验证成本**

| 级别 | 验证方式 | 人工成本 | 可回滚 | 准入策略 |
|---|---|---|---|---|
| **L0** | 编译 / 测试 / 类型检查 | ≈ 0 | 是 | ✅ 全自动，无需人工确认 |
| **L1** | 代码路径 / commit / 日志 / 记忆出处 | ~10 秒/条 | 是 | ✅ 附证据即可采信 |
| **L2** | 方案取舍 / 架构权衡 | 10–30 分钟/条，**且人须在上下文内** | 是 | ⚠️ 替身出观点，人保留决策 |
| **L3** | 排期承诺 / 发布 / 对外沟通 | 成本 = **责任本身** | **否** | ❌ 不外包 |

### 3.1 场景分级结论

| 场景 | 判定 | 依据 |
|---|---|---|
| **技术支持（答疑）** | 🟢 **现在即可落地** | 三者中**唯一自带 ground truth**——提问者自己就知道答案对不对。且大量落在 L0/L1，两周内可拿到可信度量 |
| **方案讨论** | 🟡 **可做，但须绑定证伪机制** | 已有级联 + 熔断 + 静默收敛的工程基础；风险在**共识幻觉**（见 3.2） |
| **技术排期评估** | 🔴 **不授权，降级为证据供给** | 排期不是推理题，是**历史数据拟合 + 承诺兑现**问题。且**在数据不足时没有 ground truth**——影子模式跑再久也无法判定对错（须等真实交付发生，跨月） |

### 3.2 方案讨论的关键风险：共识不等于正确

**当前配置下，多个同代模型会共享相关性盲区——它们会在同一处一起错、一起漏。** 而共识的形成恰恰消除了"分歧"这个唯一的告警信号。

因此方案讨论场景必须携带两条强制机制，否则不予准入：

1. **异见位绑定外部证伪手段**：异见结论必须携带可执行证伪路径（测试 / 复现命令 / POC diff），**不接受纯推理式反对**。仅指定"扮演反方"会退化为表演性异见——因为它没有独立证据来源。
2. **跨厂/跨代模型位固定保留**：写进机制，不靠运气。

## 4. 试点设计：用可证伪的方式证明提效

**本方案不要求评审者"相信"，只要求同意按下面设计跑一轮试点，用数据判定。**

### 4.1 首期范围（P0）

| 项 | 内容 |
|---|---|
| 场景 | 技术支持闭环（同频道内替身代替本人答疑） |
| 入站订阅 | 按**选项 B（排队不唤醒）**落地——不触碰 `main.rs:100` 的禁自主拉起设计 |
| 明确排除 | 远程 ACP dial-out；排期直接估算 |

### 4.2 度量口径（六项合并为一套）

| 指标 | 定义 |
|---|---|
| 决策延迟 | 议题开启 → 人类拍板的耗时中位数（**含人的等待**） |
| 人工介入率 | 必须人类发言才能推进的议题占比 |
| 返工率 | Agent 产出被回滚/重写的比例 |
| 往返轮次 | 单个议题内 Agent 往返次数分布 |
| 澄清问题数 | 单次答疑中需要追问的次数 |
| 平均等待时间 | 提出 → 获得响应的时间 |

**口径纪律（三条，缺一不可）：**
1. **分母必须包含 `failed` / `skipped` 运行**，否则数据自带幸存者偏差——只有活下来的运行才进统计。
2. **`skipped` 不得计入失败分子**：`skipped` = "本轮无事可做"，与"执行失败"语义不同。混算会让健康系统算出 100% 失败率。
3. **失败尝试必须逐次留档**（主键含 `attempt`），否则自动重试会抹掉失败记录，掩盖可靠性问题。

### 4.3 通过判据

| 阶段 | 判据 |
|---|---|
| **W1 本地闭环** | 三 Agent 同频道，安排**真实的人工离场窗口（8 小时）**；替身回答"本人负责模块"的历史问题；以提问者判定"是否被解决"为 ground truth |
| **W2 宿主侧收口** | 脱敏与打包下沉 Rust 侧；只读改为**进程级强制**；接入 CI/PR 历史作证据源；异见结论必须带证伪命令 |
| **准入判定** | **人工介入率 < 30% 且返工率 < 10%** → 达标方可进入方案讨论场景 |

> ⚠️ **实验设计前提**：必须安排真实的人工离场窗口。否则测到的仍是"人在线"的链路，无法证明无监督推进能力。

## 5. 我们不主张什么（边界与免责）

**明确的边界是说服力的组成部分，不是减分项。** 以下三条我们不主张，且建议写进任何立项决议：

1. **不主张排期评估可被替代。** 排期误判的后果由人承担，责任无法转移，因此签字权不能转移。Agent 可承揽的是"把估算所需的原始证据摆到桌上"，不是"替人做出承诺"。当前做法：**降级为证据供给**（建历史耗时分布 + 依赖/阻塞清单）。
2. **不主张 Agent 共识等于正确。** 见 3.2。共识必须携带溯源链（依据证据 / 反对意见 / 未验证假设）才可审计。
3. **不主张"提效"已在数据上被证明。** 当前度量基线**尚不存在**，且现有数据的三个时间列中两个不可用（见 2.4）。本文档主张的是**试点设计可证伪**，不是结论已成立。

## 7. 结论

Shinobi 对研发交付的提效赋能，最可信的表述是：

> **它把「无监督推进时长」和「并行轨道数」变成可利用的产能——前提是产出可验证、记忆可信、边界清晰。**

三句话总结落地顺序：

1. **先做技术支持**——唯一自带 ground truth 的场景，两周内可拿到可信数据。
2. **度量先行**——先让"提效"可证伪，再谈规模。所有比率类指标的分母必须含失败与跳过。
3. **人与 Agent 的分工按验证成本划分**——L0/L1 交给 Agent，L2 由 Agent 出观点人做决策，**L3 不外包**。

**本文档的立场**：本方案不请求信任，请求**一次可证伪的试点**。如果试点数据不达标，方案应当被否决——这正是它区别于"AI 提效"泛泛之谈的地方。
