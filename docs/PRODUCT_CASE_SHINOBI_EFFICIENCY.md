## 0. 一页纸结论

**读完这份文档，请你同意三件事：**

1. **提效的真实来源不是"单位时间产量"，而是"把人从关键路径上摘下来"。** 人的审阅与拍板带宽是新的瓶颈，不是 Agent 的产出速率。
2. **Shinobi 已经把"多人多 Agent 结构化推演"跑通到可日常使用的程度**——Agent 之间自动接力、有失控兜底、有收敛机制、全过程本地落库可审计。这三条都有代码实证。
3. **它当前替换不了"技术排期承诺"，也不该替换。** 我们主张的替代范围是明确的：**重复解释、串行等待、方案并行探索**这三段时间。

**一句话定位**：

> **Shinobi 替换的不是人，是「等人回话」和「把同一件事解释第三遍」这两段时间。**

**唯一必须提前告知的缺口**（详见 §3-B）：

> 「队友问你的替身，替身替你答」——**当前链路未接通**，宿主侧入站订阅未实装，且自主唤醒被设计性禁止。
> 首期落地必须包含这一项（§7 已给出不触碰安全设计的落地形态），否则该场景退化为"问自己的替身"，净价值为零。

## 1. 为什么必须重新定义"提效"

常见叙事是「AI 让一个人产出等于三个人」。**这个说法在研发交付里不成立**，因为瓶颈已经迁移：

```
旧瓶颈：人的产出速率   →   新瓶颈：人的「审阅 + 拍板」带宽
```

Agent 侧产出扩大 N 倍而决策带宽不变，净效果是**待办积压，不是提效**。这不是文字游戏，它直接决定两条工程判断：

- ❌ 错误度量：单位时间产量 —— 会奖励积压
- ✅ 正确度量：**决策延迟、人工介入率、返工率** —— 衡量人是否真的被摘出关键路径

因此本方案只有两个真实杠杆，且各自带前提：

| 杠杆 | 机制 | 前提 |
|---|---|---|
| **无监督推进时长** | 人下线，任务不下线；把"等评审/等环境/等队友"从串行改为后台并行 | 产出必须**可机器验证**，否则只是把积压生产得更快 |
| **并行轨道数** | 同一需求多条技术路线并行出观点与取舍证据，人只做收敛 | 受人的**上下文带宽**硬约束，有上限 |

**天花板结论**：L2 类产出（方案取舍、架构权衡）的吞吐上限，就是整个提效方案的上限。任何绕过它的设计只是在制造积压。

## 2. 一天的对照：把"提效"落到具体时间线

抽象杠杆说服不了人。下面是一个跨模块改动的真实形态对照。

### 2.1 旧流程（现状）

| 时刻 | 事件 | 谁在等 |
|---|---|---|
| 10:00 | 开发者 A 发起方案讨论，@ 了 B 和 C | — |
| 10:00–11:30 | **等 B 回话**（B 在开会） | A 空转 |
| 11:30 | B 回复，但缺 C 负责模块的约束 | — |
| 11:30–14:00 | **等 C 回话**（C 在别的项目救火） | A 空转 |
| 14:00 | C 回复：这个改动会碰到 3 个月前的一个坑 | — |
| 14:00–15:00 | A 重新组织上下文，把三轮碎片信息拼成一份可讨论的文档 | A 在做信息搬运 |
| 次日 | 换人接手 → 上述暗语与约束**再解释一遍** | 资深者被稀释 |

**关键观察**：这一天里几乎没有"写代码"，但交付周期被吃掉了一整天。被吃掉的不是工作量，是**人的在线时长**。

### 2.2 Shinobi 流程（现可跑） 🟢

| 时刻 | 事件 | 机制 |
|---|---|---|
| 10:00 | A 建议题、勾选 B/C 的替身，说明背景与目标 | **议题成员边界**约束参与范围（`App.tsx:130`） |
| 10:00–10:05 | 三个替身**首轮各自独立推演**，互不污染 | 议题治理机制 |
| 10:05+ | 替身之间**互相 @ 自动接力**，每次接力携带前序完整语境 | 级联接力 F1 |
| 全程 | 有 12 轮硬上限兜底；无新增量时**静默收敛**，不刷屏 | 熔断 F2 / 静默收敛 F3 |
| 全程 | 逐字流式输出，A 可随时插话纠偏（Steering） | F5 |
| 全程 | **所有消息落本地 SQLite**，可回放、可审计、不出本机 | F7 |
| 10:05+ | B、C 本人**不在链路上**，不需要回话 | ← 这就是提效 |

**收益性质的准确表述**：不是"5 分钟做完了一天的事"，而是
**"把 B、C 从链路上摘下来，并把 A 的 5 小时等待压缩成 5 分钟的收敛决策"**。

而 B、C 的替身**替换掉的正是 B、C 最不愿意做的那部分**：解释自己模块的历史约束。

### 2.3 本议题本身就是样本

本议题（`topic-1789872237972`）在库中留有 **28 条**消息记录，跨越 3 个 Agent 的多轮自动接力，全程无人转述。这不是演示环境，是正在运行的生产数据。

## 4. 边界：我们不主张什么（附三处会被核查击穿的表述）

**明确的边界是说服力的组成部分。** 一个经不起核查的能力清单，会在第一次技术评审时全盘崩塌——所以这一节请连同 §5 一起读。

### 4.1 三条不主张

| 不主张 | 原因 |
|---|---|
| **不主张排期可被替代** | 排期误判的后果由人承担，责任无法转移 ⇒ 签字权不能转移。Agent 只做证据供给 |
| **不主张 Agent 共识等于正确** | 同厂同代模型共享相关性盲区，会在同一处一起错；而共识的形成恰好**消除了"分歧"这个唯一的告警信号** |
| **不主张"提效"已在数据上被证明** | 当前度量基线尚不存在。本文主张的是**试点设计可证伪**，不是结论已成立 |

### 4.2 对外材料禁用句式（这三句必须从任何版本删除）

| 禁用句式 | 实测原因 |
|---|---|
| "Agent 可自动运行静态检查 / 测试并给出结果" | `crates/shinobi-dev-mcp/src/main.rs` 的 `tools/call` **返回硬编码常量** `"Execution completed with status: SUCCESS. 0 warnings."`——不执行任何命令，且无论输入如何都报 SUCCESS |
| "替身可在你离线时替你回答队友提问" | 入站订阅未实装，外部消息无法唤醒本机 Agent |
| "已在提效上取得 X% 提升" | 无任何指标采集链路，"提效"当前**不可证伪** |

### 4.3 三个最容易被写进 PPT、但当前站不住的说法

这三条是**提效叙事里最诱人的部分，也是最危险的部分**，请务必不要在对外版本中出现：

1. **"Agent 自带工具链，能自动跑静态检查与测试"** —— 实测 `shinobi-dev-mcp` 仅声明 **2 个**工具（README 写 4 类），且 `tools/call` 不执行任何命令。
2. **"Agent 已挂载 Shinobi 的工具集参与协作"** —— 三层证据，任一成立即否：① `acp_manager.rs:744` 在 `session/new` 载荷构造处**硬编码字面量** `"mcpServers": []`，无参数、无配置、无环境变量可写入（该 `params` 对象随后确被改写以注入 `systemPrompt`/`_meta`，**说明扩展点存在却没有写入方**——即该能力**不可达**，而非"未启用"）；② 运行时不小于 **31 / 31** 次 `session/new` 全为空数组；③ 该 MCP Server **即使挂载也无法工作**：`crates/shinobi-dev-mcp` 未实现 `initialize` 握手（落入 `_` 分支返回 `-32601 Method not found`），且 `tools/list` 声明项**缺少 MCP 必需的 `inputSchema`**，任何合规客户端会在握手阶段即中止。该 crate 虽在 workspace members 内（会参与编译），但**无任何 crate 依赖它、无任何代码引用它**——它编译，但从不运行。
3. **"纯 Rust 内核，前端只是呈现层"** —— 代码量为 Rust **2,548 行** : 前端 TypeScript **20,317 行** ≈ **1 : 8**。叙述需调整为"本地 Rust 宿主 + 前端协作台"。

## 5. 你可以自己验证（不需要相信我们）

本方案不请求信任。**以下五条命令在任何一台装了本仓库的机器上可直接复现**：

```bash
cd <repo>

# 1. 级联熔断阈值确实是 12 轮，不是文档里写的 8 或 4
grep -n "maxDepth: 12" src/App.tsx

# 2. 讨论过程确实全量落本地库（实测 messages 101 行 / 8 线程 / 2 频道）
sqlite3 shinobi_agent_memory.db "select count(*) from messages;"

# 3. 记忆确实持久化，但资产尚未形成（实测 2 条）
sqlite3 shinobi_agent_memory.db "select count(*) from acp_memories;"

# 4. 路径沙盒确实是底层强制，不是前端自律
grep -n "Path traversal outside workspace denied" src-tauri/src/main.rs

# 5. 从未挂载任何 MCP Server（31/31 全为空数组）
grep -o '"mcpServers":\[\]' src-tauri/logs/acp.log | wc -l

# 6. MCP 载荷是硬编码常量而非配置项（扩展点存在但无写入方）
grep -n '"mcpServers": \[\]' src-tauri/src/acp_manager.rs

# 7. 轮次上限两套值：执行用 12、展示落库用 8
grep -rn "maxHops: 8\|maxDepth: 12" src/App.tsx
```

**另外，这三条"陷阱"必须写进立项材料**，因为它们正是最容易被误当成结论的错误类型：

| 陷阱 | 实测 | 后果 |
|---|---|---|
| `created_at` 作时间轴 | **101 行中 72 行同为一次批量回放的同一时刻**（去重后仅 22 个不同值） | 用它算时间差会得 0，且**不报错** |
| `timestamp` 作时间数据 | 形态为 `"01:56 PM"`，**无日期** | 跨天聚合全部错误 |
| 现有运行记录判成败 | `skipped` 会被同时标记为 `completionStatus=failed`（实测 307/307） | 一个完全健康的系统会算出 **100% 失败率** |

**唯一权威时间源是消息 `id` 内嵌的 epoch。** 任何"决策延迟"类指标在时间列修复前不可采信。

## 6. 预判质疑与应答

面向真实评审场景，先把话接住。

| 质疑 | 应答 |
|---|---|
| **"这不就是 ChatGPT 群里聊天？"** | 三个可核查区别：① Agent 之间**自动接力**且携带完整前序语境，不需要人转述；② 有 **12 轮硬上限 + 静默收敛**，不会失控互喷或刷屏；③ 全过程**落本地 SQLite**，可回放可审计、不出本机 |
| **"多 Agent 一起讨论，会不会互相强化同一个错误？"** | 会，这是真风险。**共识形成会消除"分歧"这个唯一告警信号。** 所以方案讨论场景强制携带两条机制：异见位必须绑定**可执行证伪路径**（测试/复现命令/POC diff），且固定保留至少一个**非同族模型位**。仅指定"扮演反方"会退化为表演性异见 |
| **"Agent 产出变多，人审核压力不是更大吗？"** | 这正是我们重新定义提效的原因。**L2 类产出的吞吐上限就是人的连续上下文时间**，所以本方案不追求 L2 的产量提升，而是让 Agent 出观点、人只做收敛决策。度量口径选的是决策延迟与介入率，不是产量 |
| **"排期能不能让 Agent 估？"** | 不能，且我们不主张。排期是**历史数据拟合 + 承诺兑现**问题，不是推理题；且有 ground truth 之前无法验证对错（须等真实交付发生，跨月）。**降级为证据供给**：出范围/依赖/风险清单 + 历史耗时分布 |
| **"数据安全吗？会不会传到云端？"** | 宿主是**本地 ACP stdio 进程**，路径访问被沙盒限制在工作区根内（底层 `canonicalize` 强制，非 UI 自律）。但需诚实说明：记忆的**脱敏与打包目前在前端实现**，属 UI 自律而非架构强制，**这是首期必须下沉 Rust 侧的项** |
| **"你们能证明提效吗？"** | **当前不能，我们不假装能。** 所以我们不请求你相信，而是请求批准一次**可证伪的试点**（§7）。若试点数据不达标，方案应当被否决——这正是它区别于"AI 提效"泛泛之谈的地方 |

## 7. 落地路径与准入判据

### 7.1 首期范围（P0）

| 优先级 | 事项 | 依据 |
|---|---|---|
| **P0-a** | relay 订阅鉴权 + per-room 路由（替换 `relay.rs:46` 硬编码单房间 `room-acp-dev`） | **鉴权必须先于订阅**：否则中间窗口就是一条无身份校验的远程唤醒通道 |
| **P0-b** | 宿主侧入站订阅，**首期按"排队不唤醒"落地** | 不触碰 `main.rs` 禁自主拉起的安全设计，**该决策不构成阻塞** |
| **P0-c** | `messages` 加 `ts_ms`（从 id 内嵌 epoch 回填）+ `is_agent`；结构化事件落 SQLite | 现为 append-only 纯文本（`acp.log` 已达 **23 MB 且无轮转**），无法按议题聚合 |
| **P0-d** | 六项口径派生视图 + 只读健康度面板 | 原料已在 `messages` 表，**零新增采集链路** |
| **P0-e** | 脱敏/打包**下沉 Rust 侧**；只读改为**进程级**强制 | 现仅前端自律 |
| **P0-f** | `acp_memories` 增质量字段（`verified_by`/`feedback`/`last_used_at`）+ 引用回显 + 一键「不准」 | 该表被注释标注为"不可清理资产" ⇒ 错误记忆写入即终态、会随召回复利放大 |

### 7.2 度量口径（六项，分母纪律三条）

指标：**决策延迟 · 人工介入率 · 返工率 · 往返轮次 · 澄清问题数 · 平均等待时间**（全部锚定 `ts_ms`）。

分母纪律（缺一不可）：
1. **分母必须包含 `failed` / `skipped`**，否则数据自带幸存者偏差；
2. **`skipped` 不计入失败分子**（语义是"本轮无事可做"）；
3. **失败尝试逐次留档**（主键含 `attempt`），否则重试会抹掉失败记录。

### 7.3 通过判据

| 阶段 | 判据 |
|---|---|
| **W1 本地闭环** | 三 Agent 同频道；**必须安排真实的人工离场窗口（8 小时）**；替身回答"本人负责模块"的历史问题；以**提问者判定"是否被解决"**为 ground truth |
| **W2 宿主侧收口** | 脱敏下沉 Rust；只读进程级强制；异见结论必须带证伪命令 |
| **准入判定** | **人工介入率 < 30% 且 返工率 < 10%** → 达标方可进入方案讨论场景 |

> ⚠️ **实验设计前提**：必须安排真实的人工离场窗口。否则测到的仍是"人在线"的链路，**无法证明无监督推进能力**。

### 7.4 影子模式（首期验证方式）

**Agent 与人类并行给结论，只记录不执行**，跑 1–2 个月拿到准确率数据，再决定哪些环节可真正交付。影子期零权限风险：不需要唤醒授权、不写盘、不进入决策材料。

## 8. 结论

**最可信的表述是这一句：**

> **Shinobi 把「无监督推进时长」和「并行轨道数」变成可利用的产能——前提是产出可验证、记忆可信、边界清晰。**

落地顺序三句话：

1. **先做方案讨论（S1）**——已可跑，本议题就是实例；
2. **再做技术支持（S2）**——唯一自带 ground truth 的场景，但**必须先补入站订阅**；
3. **排期（S6）不外包**——责任无法转移，只做证据供给。

**本文档的立场**：不请求信任，请求**一次可证伪的试点**。
