# 🥷 Shinobi Agent 协同讨论工作台：产品需求文档 (PRD)

> **版本**：v1.0.0  
> **状态**：已评审 (Approved)  
> **面向对象**：产品经理、前端/桌面端研发、后端架构师、AI Agent 研发工程师  

---

## 1. 核心愿景与产品背景

### 1.1 背景与痛点
在现有的软件协同体系中存在两极分化的断层：
1. **传统即时协作工具（如 Slack、Discord）**：虽然支持 Channel 和多方聊天，但其信息模型纯粹面向人类设计。一旦引入 AI Bot，频繁的长文、代码块和工具日志会迅速污染公共聊天流；多轮深度推演难以沉淀，信息极易淹没。
2. **单体 AI 编程工具（如 ChatGPT、Cursor、Claude Code）**：虽然具备强大的个人辅助能力，但本质是“1对1的私密孤岛”，缺乏团队共享上下文，其他团队成员无法实时参与方案评审与推演。
3. **复杂的嵌套 Thread（树状讨论）的弊端**：传统 Reddit/论坛式的多级树状嵌套在移动端与桌面端会导致严重的空间迷失（Cognitive Overload），用户和 Agent 都难以把控当前讨论所处的真实层级。

### 1.2 产品定位
**Shinobi** 是一个 **人机平权、项目驱动、具备严格上下文隔离的多 Agent 替身协同工作台**。
- **随时参与讨论**：开发者与专属 AI 替身随时可以在功能频道中针对需求、架构、Bug 进行对话。
- **随时下钻议题**：针对复杂方案，可一键发起独立 Topic 议题进入深度推演，不阻塞主频道。
- **单层闭环收敛**：议题内部通过单层 Thread 完成论证与代码输出，讨论结束后生成“共识卡片”合流回主线，消除树状嵌套。

## 2. 空间与信息架构 (Information Architecture)

系统遵循清晰的 **“三层半扁平拓扑”**，禁止任何形式的多级递归套娃：

```text
Project (项目空间)
  │
  ├── Channel: 功能 / 需求 / 任务 频道 (按领域与交付目标划分)
  │     │
  │     ├── [普通消息] 团队即时同步、闲聊、轻量确认 (主时间轴)
  │     │
  │     └── [Topic 消息 (议题头)] 核心方案推演、技术 RFC、Agent 任务头
  │           │
  │           └── [Topic Thread 面板] 唯一的二级下钻讨论流 (单层闭环)
  │                 ├── 多轮深度问答
  │                 ├── Agent 推演过程 (Thinking Chain)
  │                 ├── 方案 Unified Diff
  │                 └── 最终共识沉淀 (Consensus Card / Resolved)
  │
  └── Channel: 另一个功能 / 任务 频道...
```

### 2.1 实体定义与职责划分

| 层级 | 实体名称 | 业务含义 | 生命周期与归属 |
| :--- | :--- | :--- | :--- |
| **L0** | **Project (项目)** | 一个完整的代码仓库或 Monorepo 模块。绑定本地工作路径、Git 仓库、全局架构规范与常驻 Agent 团队。 | 长期存在，团队顶级资产。 |
| **L1** | **Channel (频道)** | 对应一个具体的 **功能 (Feature)**、**需求 (Requirement)** 或 **任务 (Task)**。例如 `#feat-oauth2-login`、`#task-perf-leak`。 | **默认仅创建者本人可见**；其他成员（人类与 Agent 替身）必须被显式邀请加入。绑定特性 Git 分支，伴随需求直至验收归档。 |
| **L2** | **Normal Message (普通消息)** | 频道的轻量级即时消息。包含简短问答、状态同步、链接共享、表情互动。 | 流水线滚动，不承担沉重推演职责。仅对频道内成员可见。 |
| **L2** | **Topic Message (主题消息 / 议题头)** | 针对具体设计点（如架构选型、接口协议设计、复杂 Bug 排查）的正式议题头。卡片化渲染。 | 具有独立状态（`Open` ➔ `Investigating` ➔ `Resolved`）。 |
| **L3** | **Topic Thread (议题讨论流)** | 点击 Topic 消息后在右侧抽屉展开的**专属推演空间**。所有针对该议题的多轮对话、代码 Diff、Agent 工具调用在此闭环。 | **严禁再派生子 Topic**。议题解决后可折叠或归档。 |

### 2.2 频道准入与成员模型 (Membership & Access Control)

在 Shinobi 中，Channel 并非全员公开的广播大厅，而是**高内聚的功能/任务工作组**：
1. **默认仅创建者原则 (Creator-Only by Default)**：
   - 当用户（或 Agent）创建新 Channel 时，**初始成员列表中仅包含创建者本人**（以及可选自动挂载的创建者专属 AI 替身）。
   - 保证早期的功能设想、架构草稿、私密 Bug 排查具有绝对的安全与私密空间，外界无法旁听。
2. **受邀准入机制 (Invite-Only Admission)**：
   - 频道内的其余成员（人类同事、专业领域 Agent 如 `@Architect-Agent`、队友的开发替身）**必须由创建者或频道管理员显式“拉入/邀请”**。
   - 只有被拉入 Channel 的成员，其客户端才会出现在左侧导航列表并建立事件监听。
3. **消除 Agent 噪音与算力浪费**：
   - 彻底避免了“一个频道有人说话，全团队 10 个 Agent 同时争抢抢答”的混乱局面。
   - 只有被明确添加进该 Channel 的 Agent，才会在其本地进程启动该频道的上下文监控并接收任务调度。

### 2.3 频道生命周期：创建、归档与删除 (Channel Lifecycle)

Channel 作为承载功能与任务的敏捷单元，具备完整的生命周期闭环：
1. **频道创建 (Creation)**：
   - 任何项目参与者（人类或具备权限的 Agent）均可在 Project 下创建 Channel；
   - 创建时需指定分类（Feature / Requirement / Task）、频道标识名及绑定的 Git 特性分支；
   - 创建后默认状态为 `Active`，且严格遵循“仅创建者在内”的受邀准入制。
2. **频道删除与销毁 (Deletion & Teardown)**：
   - **权限控制**：**仅创建者本人（Owner）或项目管理员（Project Admin）有权删除频道**。非创建者成员只有“退出频道 (Leave)”权限，防止团队协作中出现越权误删。
   - **防误删保护 (Confirmation Guard)**：
     - 点击删除时唤出高危确认弹窗；
     - 若频道内存在尚未完结（`Open` / `Investigating`）的 Topic 议题，系统强制要求用户输入频道名称进行二次确认，杜绝误操作导致方案推演中断。
   - **级联资源自动回收 (Cascading Teardown)**：
     - **消息与议题销毁**：频道被删除后，该频道的主时间线及所有 Topic Thread 立即对所有成员失效隐藏；
     - **Agent 算力即时释放**：正在该频道推演或挂载监听的 Agent 进程/Session 立即触发平稳终止指令（SIGTERM），彻底释放本地内存、GPU 显存与 Token 占用；
     - **工作空间沙盒脱钩**：释放该频道对本地工作区文件句柄的占用。
3. **频道归档 (Archival, 软关停替代方案)**：
   - 当需求或任务开发验收完成后，创建者也可选择“归档频道 (Archive)”：保留所有历史讨论与 Topic 决策卡片作为长期可检索资产，但置为只读，Agent 不再接受新提问。

## 3. 用户与 Agent 角色模型 (Personas)

在 Shinobi 中，**“Humans and agents are just colleagues”**（人类与 Agent 互为平权同事）：

1. **人类开发者 / 架构师 (Human Developers)**：
   - 发起需求、评审方案、对关键决策与代码修改进行审批确认。
2. **专属开发替身 (Developer Alter-Ego / Managed Agent)**：
   - 代表主人的 AI 代理，具备主人的私有编程偏好记忆库（Private Memory Bank）。
   - 在主人离线或专注时，代表主人参与接口讨论、进行代码初审。
3. **公共领域 Agent (Specialist Agents)**：
   - **Architect Agent（架构师 Agent）**：擅长系统建模、RFC 编写、时序图生成。
   - **Security Reviewer（安全审查 Agent）**：负责漏洞排查、密钥泄露与并发安全审查。
   - **DevOps Agent（构建测试 Agent）**：负责触发本地测试、Lint 与打包构建。

## 4. 核心功能与业务场景说明

### 场景一：需求拆解与即时议题发起 (Feature Ideation & Topic Spikes)
1. **独立发起 Channel**：开发者 Alex 在 Project 下创建独立功能频道 `#feat-user-auth`。初始状态下，该频道**仅包含 Alex 及其影替身**，对团队其他成员和公共 Agent 保持私密隔离。
2. **邀请协作人与指定 Agent**：Alex 点击频道头部的“添加成员”，将前端负责人 Sarah、以及专业领域的 `@Architect-Agent` 显式拉入频道。此时仅有被加入的成员可以收到事件广播。
3. **主线对话**：Alex 与 Sarah 在主时间线交流：“我们需要支持微信和飞书扫码，同时兼容原有 JWT。”
4. **发起 Topic**：针对微信和飞书扫码回调冲突问题，开发者点击发送框下的 **“新建议题 (New Topic)”**，输入标题：“扫码回调统一路由与多租户适配方案”。
5. **主流效果**：主频道生成一张带有紫色边框的 Topic 议题卡片，标明 `Open` 状态。

### 场景二：Topic 内部单层深度推演 (Threaded Investigation)
1. **打开抽屉**：开发者点击 Topic 卡片，右侧滑出独立的 **Topic Thread 侧边面板**。
2. **唤醒 Agent**：在 Thread 内 `@Architect-Agent`：“请推演多租户 State 参数防篡改与回调重定向策略”。
3. **Agent 独立推演**：
   - Agent 调用 MCP 工具读取当前仓库的认证中间件文件；
   - 输出详细的交互时序图，并生成草案代码的 Unified Diff；
   - 展示透明的 Thinking Process（思考折叠区）。
4. **上下文隔离保障**：此时主频道内的其他成员正常聊天的消息，**完全不会**被加载进 Agent 的思考上下文中；同时该 Thread 内大量的代码和日志也**完全不会**刷屏主频道。

### 场景三：共识沉淀与关闭合流 (Resolution & Consensus Rollup)
1. 团队在 Thread 内达成一致，点击面板底部的 **“达成共识并标记解决 (Resolve & Merge)”**。
2. Agent 自动提炼一份 200 字以内的 **决策卡片 (Decision Record)**，内容包括：
   - 最终选定方案（如使用 HMAC-SHA256 签名的 state 参数）；
   - 涉及修改的文件路径清单；
   - 审核人名单与达成时间。
3. **合流表现**：
   - Topic 状态更新为 `Resolved`（绿色标识）；
   - 决策卡片作为该 Topic 卡片的摘要直接展示在主时间线；
   - 主时间线成员无需翻看 40 条回帖即可清晰获知结论。

+-------------------+--------------------------------------------+-----------------------------------------+

### 5.2 核心交互细节
1. **Topic 视觉强化**：
   - Topic 卡片与普通单行气泡有明显层级差，展示主题名称、当前状态徽章、参与人员头像栈、最新一条回复的预览。
2. **快速下钻**：
   - 点击 Topic 卡片任意区域，右侧抽屉在 200ms 内滑出；主时间轴背景轻微变暗或保持双栏平行对照。
3. **Esc 键或右上角快速关闭**：
   - 随时关闭抽屉返回主频道，不丢失正在编辑的内容草稿。
4. **移动端 / 窄屏适配**：
   - 当屏幕宽度 < 1024px 时，Thread 抽屉以全屏 Overlay 形式覆盖呈现，顶部提供明确的“返回主频道”箭头。

## 6. 非功能性需求 (NFR)

1. **响应延迟**：
   - 本地 Nostr Relay 广播通知延迟 $< 10\text{ms}$；
   - 切换 Channel 或展开 Topic 抽屉响应时间 $< 100\text{ms}$。
2. **安全与隔离**：
   - Agent 执行工具仅限于绑定的 `localWorkspacePath` 目录，禁止路径穿越攻击（Path Traversal）。
   - 不同 Topic 之间严格通过独立的会话上下文边界进行隔离，防止私有凭证或讨论信息跨议题外泄。
3. **低噪音原则 (Zero-Noise Default)**：
   - Topic 内的每一条推演消息默认不对频道其他成员推送全屏红点，仅在成员被明确 `@` 或点击关注该议题时产生提醒。
