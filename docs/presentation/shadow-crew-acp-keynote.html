01 / 协作

单 Agent 与多 Agent：两种工作方式

不比较优劣；先看任务边界、验证需求与协调成本。

SINGLE AGENT

单 Agent：链路短，上下文集中

一个执行体从头做到尾，适合边界清晰、可一次交付的任务。

  • 工作方式：读仓库、改文件、跑测试，一条链路完成
  • 优势：上下文集中，协调成本低
  • 代价：单点认知偏差，缺少外部挑战
MULTI-AGENT

多 Agent：角色分工，交叉验证

把任务拆成角色与步骤，适合高风险、跨领域、需要证据链的任务。

  • 工作方式：提案、红方质询、落地验证、收敛
  • 优势：多视角交叉检查，任务可拆解
  • 代价：协调、Token 与时延上升，可能出现伪协同
目的协作不是“更强”，而是把过程交给工作流：人从执行细节里退出来，只对结果负责。
是否更好，取决于任务；这里不做一刀切判断。 论文依据与边界见附录 A7
02 / 问题

协作的三个工程问题

工具越来越多，但协作仍有三个问题：认知、经验、收敛。

PROBLEM 01

认知盲区

单模型自审有边界，缺少外部角色提出可证伪的反例。不是“单 Agent 不行”，而是需要交叉验证。

  • 表现：同一模型反复自审，结论趋同
  • 缓解：异构角色做红队质询
需要外部挑战单模型归纳偏置
PROBLEM 02

记忆孤岛

同事调优好的领域规约与项目记忆锁在某台机器。换人、换机、离职后，经验难以复用。

  • 表现：换机 / 换人后重新教
  • 缓解：经验打包成可分发资产
经验不可迁移资产随人离线
PROBLEM 03

协作失真

多 Agent 讨论容易出现附和、复读、无收敛。问题不在多 Agent 本身，而在缺少角色约束与验证机制。

  • 表现：轮次增加，结论不收敛
  • 缓解：角色约束 + 验证门禁
需要收敛机制不是多 Agent 的错
验证门禁 结论进入裁决前，先过四道检查：证据可复现、反例逐条回应、一致性达标、法定人数参与；缺证据就退回，不按“看起来一致”放行。

三个问题的共同解：标准化连接 + 资产化记忆 + 可验证的收敛机制。

05 / 控制面

ACP 之上，宿主补了什么

协议只到「宿主 ↔ 单个 Agent」；多 Agent 协作要的兜底、会话、上下文与质量保障，都在宿主侧。

06 / 协议

从 V1 到 V2：调用模型变了

最大的变化不是字段，是 prompt 的生命周期：V1 同步挂起到结束，V2 插入即返回、异步报状态。

V1同步挂起
session/prompt 推理 + 工具 + 多轮模型交互，全挂在这一个请求里 ↩ stopReason
中途想补一句话，只能先 session/cancel 再来；客户端也不知道“进行到哪一步”。
V2立即确认 + 异步
session/prompt ↩ { messageId } › session/update：running → tool_call → … → idle(stopReason)
消息插入会话就返回；执行在后台继续，进度与终态都靠 state_update 变体上报，运行中还能继续投递新消息。
V1Stable · 整数 1
版本：客户端报 1；Agent 回自己支持的最高版
能力：布尔清单，fs.readTextFile: true 表示“我能读文件”
客户端工具：fs/*、terminal/* 写在协议里，由客户端执行
会话恢复：load 重放全部历史；resume 是可选能力
认证与配置：authenticate / logout；set_mode 与 set_config_option 并存
STABLE
V2Draft · 整数 2
版本：Agent 回 ≤ 请求的最高版；没有匹配就 -32022，客户端断开
能力：对象“存在即支持”，session: {} = 会话基线，session.mcp.stdio: {} = 支持 stdio MCP；不写 = 不支持
客户端工具：fs/*、terminal/* 全部移除，改由 MCP 提供
会话恢复：load 移除；resume 必选，可带 replayFrom 从指定位置重放
认证与配置：auth/login + auth/logout 成对；set_mode 并入 set_config_option
DRAFT
结论 其余差异都围绕调用模型收敛：状态可追踪（state_update）、能力可协商（对象标记）、版本可拒绝（-32022）；但 V2 仍是 Draft，落地要双栈。
07 / 协议

六维差异，逐项对账

同一份协议，两代生命周期；差异不在功能，而在“完成”与“能力”怎么定义。

维度 ACP V1 ACP V2 Shadow Crew 的演进应对
版本协商 整数 1；Agent 返回自己支持的最新版 整数 2；取 ≤ 请求的最高版无匹配返回 -32022（requested / supported） 先读版本，再校验参数；v1/v2 两套 handler
能力模型 agentCapabilities / clientCapabilities布尔：true / false capabilities 对象 + 必填 info存在即支持（{}）；省略 = 不支持；session 为基线 存在性判断，不做布尔等值；按连接选版本
Prompt 生命周期 同步阻塞：挂起到回合结束响应 { stopReason }；中途补话要先 cancel 异步：插入即 ack { messageId }执行在后台；running / idle 走 state_update UI 不能把 prompt 响应当完成；终态看 idle

09 / 工具

读写谁来做：端点优先，宿主兜底

默认让端点用自己的工具；端点没有对应能力时，宿主 MCP 才补位。治理类工具始终在宿主。

① 默认路径

端点用自己的工具

read / write / edit / grep / glob / shell 都在 ACP 端点进程内执行。宿主挂 governance_only：基础读写与终端工具不出现在 tools/list，调用直接被拒。

go test · cargo test · 语言工具链
缺失时
② 兜底路径

宿主 MCP 补位

端点没有对应能力时，dev MCP 以 full 提供 read_file / write_file / str_replace / list_dir / search_code / shell。

SHADOW_CREW_DEV_MCP_PROFILE=full
③ 治理工具

两种 profile 都保留

submit_* 结构化契约、artifact 写入、validate_workspace_diff 始终由宿主提供，不随 profile 变化。

governance_only ⊂ full
为什么优先端点工具跑在端点进程里，能用到它自己的缓存、沙箱与语言工具链；宿主重复实现会变成两套权限语义，也容易和端点的编辑策略打架。
唯一硬边界不管工具在谁手里，越界路径都进宿主 ACP 权限审批；full profile 下的 fs / shell 也额外加了 workspace 校验。

当前实现：本地 super-agent 的 session 统一注入 SHADOW_CREW_DEV_MCP_PROFILE=governance_only；full 供无原生工具的端点显式启用。

10 / 会话

每个单元，一个会话，一个工作区

频道、议题、私聊、模块分治各自独立：不同 session key，不同工作目录，互不串上下文。

单元session 维度工作目录
Channelchannel:<cid>:<room>~/.shadow-crew/channels/<cid>
Topictopic:<cid>:<room>:<mode>…/channels/<cid>/topics/<tid>
DMdm:<agent>:<room>~/.shadow-crew/agents/<aid>
DM Topicdmtopic:<agent>:<room>:<mode>…/agents/<aid>/topics/<tid>
Module模块沙箱 + allowedFiles同一 binding 内的白名单子集

四种协作单元的 key 由宿主拼接，工作目录由 workspace binding 解析；模块层再叠一层上下文沙箱与文件白名单。

  • 建立即锁定
    session/new 的 cwd 由宿主解析并绑定，不由对端自由指定
  • 运行期不可变
    中途切换目录的请求被拒绝，而不是“尽量兼容”
  • 并发互不越界
    多议题并行时，各自的写入落在各自目录
  • 模块级隔离
    每个模块只注入「公共契约 + 本模块规范 + 本模块历史」，只改 allowedFiles 内的文件
Agent 可以很自由，但它的世界必须有边界。
11 / 私聊

私聊：按 Agent 连续，按议题切开

私聊不绑项目目录，让同一个 Agent 的历史连贯；长对话会膨胀，所以私聊也有了议题。

① 主私聊 · 按 Agent 连续
sessiondm:<agent>:<room>
cwd~/.shadow-crew/agents/<aid>

不绑定项目目录。换项目继续聊，还是同一条历史、同一份记忆；代价是聊久了上下文会越滚越大。

② 私聊议题 · 按问题切开
sessiondmtopic:<agent>:<room>:<mode>
cwd…/agents/<aid>/topics/<tid>

只讨论特定问题：独立 session、独立目录，聊完不回流，主私聊不会被撑大。

议题目录的三种来源
  • default：新建独立目录，从零开始
  • agent_snapshot：继承当前私聊 cwd，接着聊，但产物隔离
  • custom：自选目录，适合临时验证
产物永远落在 <aid>/topics/<tid>/artifacts，不和主私聊混在一起。
3 个独立 session key dm / dmtopic 命名空间
取舍 绑项目 = 同一个 Agent 的历史被切成多份；不绑 = 连贯，但上下文会变大。所以用议题切开：要连贯走主线，要聚焦开议题。
12 / 频道

普通讨论：靠 @ 接力，用沉默收敛

默认模式下没有固定轮次，也没有总指挥；谁被 @ 谁发言，没人被 @ 就停。

① 接力

@ 是唯一的接力棒

用户或 Agent 在正文里 @ 谁，谁被唤醒；没被 @ 的人在听，不抢话。不同角色不会被“轮询”到。

② 收敛

没有 @，讨论就结束

本轮无人发出有效 @，级联直接终止：不弹提示、不加系统消息。沉默本身就是“已达成”。

③ 兜底

到顶也不打断

LoopGuard：12 跳或单 Agent 8 次，到顶静默收口，不投熔断卡片、不打断阅读。

支线 Swarm：显式触发，一个拆、多个做、一个收
/swarm 或输入框开关 → Lead 拆解 + allowedFiles → 人工确认 + 冲突检测 → 子房间并行 · 禁横向 @ → Lead Reduce 汇总
设计初衷 不让 Agent 为了“表态”而发言：没有增量就不开口，达成共识就散场。省 Token 也省人的注意力——需要拆分时再显式开 Swarm，需要对抗时再升维 4+1。

17 / 决策

防谄媚：契约优先，词表兜底

有结构化答辩就读契约，没有才降级到 AST 证据；最后用 BSS 与 γ 折减。

①结构化优先不看词表
  • full_surrender_without_patch 且无补丁 → DSS 0.92（受质询）/ 0.82，直接判投降
  • 基准：reject / uphold 0.08，partial 0.22；让步多于坚守且无补丁 +0.35
  • 每个补丁 −0.05（上限 −0.12），有量化指标再 −0.04，封底 0.05
②文本兜底零正则 AST
  • 结构证据：量化指标 ≤0.35、分点 ≤0.30、代码引用 ≤0.25、长度 ≥150 加 0.15
  • 抵扣：工程词 0.20 + 逻辑词 0.16 + 结构分 0.45
  • 判投降：≥2 个谄媚词且无代码 / 分点 / 缓解词
③先验与折减BSS + γ
  • BSS 查表：推理模型 0.18 / 旗舰 0.32 / 小模型 0.55 / 默认 0.35
  • γ = 1 − min(0.60, 0.40·DSS + 0.20·BSS)
折减之后，用到三个地方
SPRT
防伪早停0.90 的高一致分被拉回 0.763，推不动提前收敛
BWM
置信度降权谄媚度进校准置信度矩阵，压低该发言权重
G-FRAME
模块健康分DSS > 0.45 时扣 (DSS−0.45)×0.4
算一遍
设 DSS = 0.68、BSS = 0.35
惩罚 = 0.40×0.68 + 0.20×0.35 = 0.342
折减 γ = 0.658，原始分 0.90 →
0.5 + (0.90−0.5)×0.658 = 0.763

收缩是不对称的：正面分往 0.5 强拉，负面质疑只轻微收缩，避免误伤合理挑战。

不是要求模型“别谄媚”，而是让服软不加分、带证据的反驳才加分。 Sycophancy Propagation · Free-MAD

附录 A1 / 实操

一次 ACP 调用，从头到尾

initialize 握手 → session/new 锁定工作区 → session/prompt 投递 → session/update 流式回传 → permission 反向审批 → idle 收口。

1initialize · protocolVersion / capabilities / infoC → A
2auth · authMethods 非空时；v2 auth/login，v1 authenticateC → A
3session/new · cwd + mcpServers → sessionIdC → A
4session/prompt · ContentBlock[]；v2 立即 ack { messageId }C → A
5session/update · 消息 / 工具 / state_update；需要时 request_permissionA → C
6idle · v2 state_update { stopReason }；v1 prompt 响应 { stopReason }A → C
V1 · 回合制
prompt 挂起到回合结束
session/prompt 的响应就是终态：{ stopReason }。
V2 · 插入即确认
prompt 只 ack 插入
响应是 { messageId }；前台进度与终态走 state_update。
三条分支
session/cancel session/resume session/close
取消等 idle(cancelled)；恢复可带 replayFrom；关闭先取消再释放。
先记住这条主干；A2 讲 capabilities，A3 / A4 展开方法，A5 给出可直接照抄的报文。 来源：agentclientprotocol.com
附录 A2 / 基础

capabilities 是什么：握手时交换的能力清单

它不是权限，也不是功能开关；它是 initialize 时交换的“能力清单”。

字段声明后可用
sessionnew / list / resume / close / prompt / cancel / update 七个基线方法
session.prompt.imageprompt 里可带 image 内容块
session.prompt.audio可带 audio 内容块
session.prompt.embeddedContext可带 resource 内嵌资源
session.mcp.stdiosession/new 可传 stdio MCP server
session.mcp.http可传 HTTP MCP server
session.deletesession/delete 可用
session.additionalDirectories可带额外工作区根目录
session.systemPrompt可带 append / override 系统提示词
auth.terminal（Client）Agent 可提供 terminal 类型登录
elicitation（Client）elicitation/create 可用

v1 用布尔标记（true/false）；v2 用对象标记（{} / 省略）；省略 = 不支持。

V2 · 一段真实的 capabilities
// Agent 声明：支持基础 session + 图片 + stdio MCP ← {"capabilities":{ "session":{ "prompt":{"image":{}}, "mcp":{"stdio":{}} } }}
  • 不是权限
    权限走 session/request_permission；capabilities 只说明“支持哪些可选面”。
  • 不是版本
    版本是 protocolVersion；能力是同一版本内的可选字段。
  • 不要猜
    对端没声明的类型不要发；发了可能返回 -32602。
一句话capabilities = “我能接什么”的清单；session 是总开关，声明它就要实现七个基线方法。

附录 A4 / ACP V2 (Draft)

V2 方法地图：基线更大，客户端更薄

一个连接只跑一个版本；先看基线，再看六个断点。

方向方法必需性用途
C → Ainitialize基线protocolVersion / capabilities / info → 版本 + 能力
C → Aauth/login · auth/logoutauthMethodsmethodId → 登录 / 登出结果
C → Asession/new基线cwd + mcpServers + systemPrompt → sessionId
C → Asession/list · resume · close · delete基线 / delete 能力sessionId / cursor → response / 列表
C → Asession/prompt基线ContentBlock[] → { messageId }
C → Asession/cancel通知sessionId（无响应）
C → Asession/set_config_option按能力configId + value → response
A → Csession/update通知sessionId + update（无响应）
A → Csession/request_permission基线title + subject + options → outcome
C → Atool_call/cancel · terminal/cancel按能力toolCallId / terminalId → response

表中“→”后为返回；通知无响应。state_update 是 session/update 的变体，不是独立方法。v2 基线方法更多，但客户端不再实现 fs/* 与 terminal/*。

V1 → V2 六个断点
  • Prompt：响应只 ack { messageId }；终态看 state_update
  • 恢复：load 移除；resume + replayFrom
  • 客户端工具：fs/terminal 移除；客户端工具走 MCP
  • 能力：统一 capabilities + 必填 info；对象标记
  • 认证：authenticate/logout → auth/login/logout
  • 工具报告：tool_call 移除；tool_call_update upsert
STATUS
V2 仍是 Draft
把 v2 放在特性开关后；v1 端点继续保留。不要用结构体互转伪装双栈。
基线 声明 capabilities.session 就必须实现 new / list / resume / close / prompt / cancel / update；缺一不可。
附录 A5 / 接入

最小接入：四段报文跑通 ACP

以 stdio + v2 为例。直接照抄，先让一条消息走通，再补能力。

1 · INITIALIZE
// 先版本，后能力 → {"jsonrpc":"2.0","id":0,"method":"initialize","params":{ "protocolVersion":2, "info":{"name":"my-client","version":"1.0.0"}, "capabilities":{}}} ← {"jsonrpc":"2.0","id":0,"result":{ "protocolVersion":2,"capabilities":{"session":{}}, "info":{"name":"my-agent","version":"1.0.0"},"authMethods":[]}}
2 · SESSION / NEW
// cwd 必须是绝对路径 → {"jsonrpc":"2.0","id":1,"method":"session/new","params":{ "cwd":"/repo","mcpServers":[]}} ← {"jsonrpc":"2.0","id":1,"result":{"sessionId":"sess_1"}}
3 · PROMPT
// v2：插入即 ack，不等回合结束 → {"jsonrpc":"2.0","id":2,"method":"session/prompt","params":{ "sessionId":"sess_1", "prompt":[{"type":"text","text":"review this"}]}} ← {"jsonrpc":"2.0","id":2,"result":{"messageId":"msg_1"}}
4 · UPDATE + PERMISSION
// 终态；需要时反向审批 A→C {"jsonrpc":"2.0","method":"session/update","params":{ "sessionId":"sess_1","update":{"sessionUpdate":"state_update", "state":"idle","stopReason":"end_turn"}}} A→C {"jsonrpc":"2.0","id":5,"method":"session/request_permission", "params":{"sessionId":"sess_1","title":"Allow edit?", "subject":{"type":"tool_call","toolCall":{"toolCallId":"call_1"}}, "options":[{"optionId":"allow-once","name":"Allow once","kind":"allow_once"}]}} C→A {"result":{"outcome":{"outcome":"selected","optionId":"allow-once"}}}
stdio：每行一个 JSON-RPC 对象，UTF-8，禁止内嵌换行；stdout 只写 ACP 消息，日志走 stderr。 V1 差异：clientCapabilities + clientInfo；prompt 响应在结束时返回 stopReason
附录 A6 / 落地

接入检查清单：从握手到收口

十项检查，覆盖传输、版本、能力、会话、流式、权限与恢复。

01 / TRANSPORTstdio 按行传输每行一个 JSON-RPC 对象；stdout 只写 ACP；日志走 stderr；不发送 batch。
02 / VERSION先读 protocolVersionv2 取 ≤ 请求的最高版；无匹配 -32022；一个连接只跑一个版本。
03 / CAPABILITIES只发对端声明的能力v2 看对象是否存在；v1 看布尔；省略即不支持。
04 / SESSIONcwd 是契约必须绝对路径；resume 重发同一个 cwd 与完整 mcpServers 列表。
05 / CONTENT基线只有 text / resource_linkimage、audio、resource 需要 prompt 能力；空 prompt 直接拒绝。
06 / STREAM按序应用 session/updatev2 upsert：省略=不变，null=清空，chunk=追加。
07 / PERMISSION审批要有上下文title 必填；subject 用 tool_call / command；至少一个 option。
08 / CANCEL取消不是错误session/cancel 是通知；等 idle stopReason=cancelled，不要展示为失败。
09 / RESUME重放要有边界replayFrom:start → replay_complete → 当前 state_update → response。
10 / DUAL-STACK两套 handler + 特性开关v2 仍是 Draft；不要用消息翻译伪装兼容，v1 端点继续保留。
-32601 方法不存在 -32602 参数错误 -32002 会话不存在 -32022 版本不支持 -32800 请求取消
来源：agentclientprotocol.com · v1 / v2
附录 A7 / 依据

参考论文与适用边界

这些研究支持“多角色、任务拆解、验证机制可能提升准确性”，但结论有任务与模型边界。

PAPER 01

Free-MAD

反从众的多 Agent 辩论；挑战者迫使提案给出可证伪反例。

PAPER 02

ColMAD

协作式多 Agent 辩论；角色分工与协同增量。

PAPER 03

LMAD

局部多 Agent 辩论；按冲突切片，减少无关上下文。

PAPER 04

ReConcile

异构模型共识与置信度校准；用校准置信度而非简单投票。

PAPER 05

Sycophancy Propagation

谄媚在多轮讨论中传播；需要量化与信任折减。

PAPER 06

DIANOIA

角色正交的认知流程；4+1 阶段划分的依据之一。

PAPER 07

LLM + BWM

用 BWM 把准则权重变成可检查的数学问题。

PAPER 08

Disagreement-Aware

保留少数派异议与黑天鹅重启触发器。

G-FRAME内部规范，不是论文：用贝叶斯先验 / 后验做模块路由（宣讲中称“贝叶斯博弈”），把大任务拆成 2–4 个原子模块。
引用边界：论文结论依赖任务、模型与提示；这里不主张“多 Agent 必然优于单 Agent”。 来源：论文原文 / 内部规范
