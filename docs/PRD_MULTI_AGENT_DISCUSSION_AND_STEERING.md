## 1. 核心愿景与问题定义

### 1.1 背景与痛点
在多 Agent 协同工作台（如 Shinobi）中，当引入多个具备自主行动能力的 AI 替身（Alter-Ego）与领域专家 Agent 时，跨 Agent 讨论（Agent-to-Agent Coordination）极易产生以下三大严峻失控问题：

1. **“死循环礼貌风暴”（Runaway Ping-Pong Loop）**：
   - 当多个 Agent 拥有互相提问、委派与确认的自主权时，传统设计中简单的“收到消息必须回复”与“完成工作必须 @ 对方”规则会形成恶性增强回路。
   - 在真实工程案例中，曾出现连续 **21+ 轮**互相表达客套与挂起的无效死循环（*“我已挂起，没任务不再回复 @AgentB” ➔ “收到，我也挂起 @AgentA” ➔ “确认收到...”*），造成大量的 Token 浪费、GPU 算力耗尽与公共通知轰炸。
2. **“讨论无限发散与无边界死磕”**：
   - 面对复杂的架构分歧或边界 Bug，两个 Agent 可能在缺乏全局大局观的情况下就微小实现细节不断来回辩论，轮数无节制增长，导致人类开发者产生严重的认知过载与等待焦虑。
3. **“中途插话粗暴中断与上下文割裂”**：
   - 当人类在 Agent 推演过程中发现方向偏离并尝试纠偏时，传统工具往往只有“直接杀死任务重新提问”或“排队等待 Agent 跑完错误逻辑”两种极端选择，导致已计算的有效推理被粗暴丢弃，或错误逻辑持续空耗算力。

### 1.2 产品核心哲学
为了解决上述痛点，Shinobi 遵循四条核心治理法则：
* **人机平权（Humans and agents are just colleagues）**：Agent 具有独立的身份与发言权，但在讨论生命周期中必须遵循严格的团队公约。
* **局部信息价值法则（Local Information Value）**：不能笼统要求模型全局“不要循环”，而是将治理下沉为单轮可判定的局部规则——**“本次回复是否为当前议题提供了增量信息？”**。
* **静默即成功（Silence is explicitly a success）**：当没有实质新信息可贡献时，Agent **不发送任何消息即为成功**。
* **Steering 融合插话（Steering Fusion）**：人类在讨论推演过程中的插话不应盲目覆灭前序工作，而应以“注入引导 (Steer)”的融合姿态无缝渗入推理链条。

## 2. 讨论话题轮数控制模型 (Discussion Turns Governance)

### 2.1 轮数计量与人机差异化策略

在 Shinobi 中，讨论话题（Topic Thread）设立了清晰的“轮数预算”模型：

```text
[Topic Thread 启动]
       │
       ▼
 连续未介入轮数 counter = 0
       │
       ├── Agent 发言 ──► counter += 1 ──► 检查是否触及熔断阈值 (Max = 8)
       │                                         │
       │                                         ├── 未触及 ➔ 正常流转
       │                                         └── 达到 8 ➔ 触发熔断挂起 (Circuit Breaker)
       │
       └── 人类发言 ────► counter = 0 (立即清零计数器，注入新指引)
```

1. **Agent-to-Agent 轮数计算（Unbroken Consecutive Turns）**：
   - 仅统计在没有人类参与的情况下，连续由 Agent 自发产生发言的轮次。
   - 经过大量真实技术论证场景测算，绝大多数高内聚架构推演在 **3 ~ 5 轮** 内即可达成有效共识，将连续讨论安全阈值定为 **8 轮**。
2. **人类参与即时清零**：
   - 只要任何人类开发者在 Thread 中发送任何指导、确认或纠偏，`consecutive_agent_turns` 计数器**立即重置为 0**，赋予 Agent 团队在新输入下的完整推演预算。
3. **人机回复准则差异**：
   - **人类向 Agent 提问**：Agent **必须回复**（即便是“暂无新发现”或“暂无法处理”，绝不让开发者面临静默假死）。
   - **Agent 之间提问/协作**：Agent **有条件回复**（仅当产出代码、决策、结论、关键阻塞时才发言；否则一律静默）。

### 2.2 界面交互：轮数状态指示器 (Turns Indicator)

在 Topic Thread 抽屉面板顶部右侧，提供直观的讨论健康状态徽章：

| 连续轮数区间 | 视觉呈现 | 状态定义 | 交互行为 |
| :--- | :--- | :--- | :--- |
| **1 ~ 4 轮** | `🟢 讨论活跃 (3/8)` | **健康快速推演** | 点击展开微型时间线，查看各参与 Agent 轮次分布。 |
| **5 ~ 7 轮** | `🟡 深度收敛中 (6/8)` | **逼近建议上限** | 提示悬停：“Agent 正在进行深度论证，建议人类参与指导”。 |
| **≥ 8 轮** | `🔴 讨论熔断挂起` | **触发自动熔断** | 讨论区自动冻结，主推演区展示高亮处置卡片。 |

### 2.3 议题成员准入机制：严格限定频道内 Agent 成员 (Channel-Scoped Agent Admission)

在 Shinobi 的信息拓扑中，Topic Thread 是 Channel 下属的单层闭环推演空间，因此**议题的成员范围必须严格受限于其所属频道的成员边界**（$Members_{Topic} \subseteq Members_{Channel}$）：

1. **新建议题时的选择限制 (Strict Dropdown Scope)**：
   - 用户在点击“新建议题”弹窗中指定参与讨论的 Agent 成员时，候选列表**仅展示当前 Channel 现存的 Agent 成员**；
   - 绝不展示项目下其他未加入当前频道的 Agent，从交互源头杜绝未授权 Agent 接触频道的私有业务上下文。
2. **未加入频道的外部 Agent 引入引导 (Admission Guidance & Onboarding)**：
   - 若用户确需引入外部专家 Agent（例如当前频道仅有 `@Alex替身`，现需引入 `@Security-Bot` 审查代码）：
   - 系统在选择器下方提供明确指引与快捷入口：*“目标 Agent 尚未加入当前频道。请先将其添加至频道成员列表，方可邀请参与议题讨论”*；
   - 具备管理员权限的成员可一键触发“添加 Agent 至频道并加入本议题”，完成两级显式授权。
3. **推演过程中的 @ 偷渡防御 (In-Thread Mention Guard)**：
   - 在 Topic Thread 讨论过程中，任何发言（无论是人类还是 Agent）若尝试 `@` 未加入当前频道的 Agent，输入框与消息引擎将进行硬拦截并报错：
     > *“无法提及该 Agent：该 Agent 尚未加入本频道。请先将其加入频道后方可参与讨论。”*
   - 彻底杜绝通过 Thread 消息“偷渡”未受邀 Agent 导致上下文泄漏的风险。

## 3. 三合一讨论终止机制 (Three-Fold Termination Mechanism)


Shinobi 明确采用 **“方案一（静默自然收敛） + 方案三（熔断机制强制刹车） + 方案四（人类主持人介入强行关停）”** 组合方案，形成从“底层自主平稳收敛”到“中间系统级防死锁兜底”，再到“顶层人类绝对控制权”的三维一体闭环。

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   Shinobi 多 Agent 讨论三合一终止体系                   │
│                                                                        │
│   [顶层控制] 方案四：人类主持人介入强行关停 (Human Moderation / Abort) │
│       ▲       • 随时点击“结束讨论”或“强制终止”                          │
│       │       • 立即向 Agent 广播取消信号，释放沙盒算力                 │
│       │                                                                │
│   [系统兜底] 方案三：连续轮数熔断强制刹车 (Hard Circuit Breaker)        │
│       ▲       • 连续无人类介入达 8 轮时自动截断                        │
│       │       • 冻结自动事件触发，插入熔断告警卡片，等待人类仲裁        │
│       │                                                                │
│   [自主收敛] 方案一：静默自然收敛 (Silence as Completion)              │
│               • 基于局部信息价值法则，无实质增量即停止发送             │
│               • 严禁“收到/好的”客套，总线静默后讨论自然完结            │
└────────────────────────────────────────────────────────────────────────┘
```

### 3.1 方案一：静默自然收敛（底层自主收敛）
* **产品逻辑**：
  - 每一个参与讨论的 Agent 在完成思考与工具调用后，都会在本地做出判断：*“我的输出是否包含了新的代码 Diff、实质性结论、架构决策或关键阻碍？”*
  - **严禁裸确认（No Bare Acknowledgements）**：如果输出仅包含“收到”、“已对齐”、“同意上述观点”、“我不再回复”等礼貌性确认，**该 Agent 被严格禁止向频道发送该消息**。
  - 当所有参与方均得出无增量可发送时，Nostr 消息总线上不再有新事件产生，讨论在没有任何多余噪音的情况下自然平稳完结。

### 3.2 方案三：连续轮数熔断强制刹车（中间系统级防死锁兜底）
* **产品逻辑**：
  - 若两个或多个 Agent 因为逻辑歧义或 Prompt 冲突，连续来回交互达到 **8 轮** 且中途无人类发言，系统内置的 **Circuit Breaker** 立即生效。
  - **交互表现**：
    1. 立即阻断后续 Agent 的自动触发；
    2. 在 Thread 时间轴末端生成带有鲜明警示样式的 **【讨论熔断挂起卡片】**；
    3. 卡片提供快捷操作：“输入补充指引以重置继续”、“采纳当前草案并结束”、“丢弃本次推演”。

### 3.3 方案四：人类主持人介入强行关停（顶层人类绝对控制权）
* **产品逻辑**：
  - 人类开发者始终是当前项目与频道的最终负责人（Moderator）。
  - 在 Topic Thread 面板的顶部操作栏与底部输入区，常驻两个明确的控制按钮：
    - **【结束讨论并沉淀 (Resolve & Close)】**：确认当前推演成果，将议题标记为 `Resolved`，自动提炼决策摘要回填主频道，并关闭 Thread 的继续发言权限。
    - **【强制终止 (Abort / Kill)】**：当发现推演严重偏离或陷入死循环时，一键强制终止所有正在执行的 Agent 后台进程，撤销未持久化的文件修改，释放本地算力。

## 4. 中途插话与中断：Steering 融合模式

当 Agent 正在针对某个复杂议题调用 MCP 工具、分析代码或连续生成长篇方案时，人类开发者若希望补充约束条件、纠偏方向或插入新话题，Shinobi 采用 **Steering 融合模式 (Steering Fusion)**。

### 4.1 Steering 模式的核心交互理念
传统协作中的插话往往是“要么硬杀死重来（导致之前几分钟分析全白费），要么排队等跑完（白白看着错的跑到底）”。  
**Steering 融合模式** 的核心是：**“在飞行中微调航向 (In-Flight Course Correction)”**。
* 不粗暴废弃 Agent 已读取的文件和初步推理；
* 将人类新输入的消息定义为 **“伴随到来的转向指令 (Steering Directives)”**；
* 引导 Agent 在原有工作的基础上将新指令**编织吸收 (Weave In)**，而不是全盘放弃或机械割裂。

### 4.2 用户插话的两种场景与交互形态

```text
+-----------------------------------------------------------------------------------------+
| [Topic Thread 底部输入栏]                                                                |
|                                                                                         |
| ┌─────────────────────────────────────────────────────────────────────────────────────┐ |
| │ 请注意：数据库迁移脚本必须兼容 Postgres 14，不要使用 pg16 的新增语法。              │ |
| └─────────────────────────────────────────────────────────────────────────────────────┘ |
|                                                                                         |
|  [⚡ 注入引导 (Steering) ▼]     [📎 附加代码]    [@ 提及 Agent]     [发送 Steering 纠偏 ➔] |
|   ├─ ⚡ 注入引导 (Steering - 默认): 将新补充融入正在推演的任务中                          |
|   └─ 🛑 紧急打断 (Interrupt): 立即放弃当前推演，以此需求重新发起                          |
+-----------------------------------------------------------------------------------------+
```

1. **场景 A：实时注入引导 (Default: Steering Mode)**
   - **用户意图**：“我看到你在写了，但别忘了补充这个边界条件。”
   - **交互响应**：点击发送后，UI 呈现轻量级流式注入动画，Agent 思考流（Thinking Process）中立即呈现 *“已接收人类中途指导，正在融入当前设计...”*，生成内容无缝转为兼顾新约束的实现方案。
2. **场景 B：紧急打断重定向 (Interrupt Mode)**
   - **用户意图**：“方向全错了，需求变了，立刻停下并按新的来。”
   - **交互响应**：下拉切换至“🛑 紧急打断”，系统立即中止当前执行，原推演被标记为“已打断”，Agent 专心根据新指令重新开始工作。

### 4.3 派生旁路议题 (Side-Topic Forking)
* 当人类插入的话题虽然重要，但不属于当前议题的核心主线（例如在讨论登录逻辑时突然想到“我们稍后需要单独评估 Redis 集群高可用”）：
* 可以在该消息气泡上点击操作菜单：**“派生为新议题 (Fork as Side-Topic)”**；
* 系统将在当前频道主时间线上派生一张独立的 Topic 议题卡片，分配独立的 `SessionScope::Thread`，既不污染当前的讨论上下文，又确保了新话题不被遗漏。

## 5. 界面原型与交互细节 (UI/UX Specification)

### 5.1 议题面板与熔断警示卡片原型

```
+-----------------------------------------------------------------------------------------+

|                                                                                         |
| [Security Bot]:                                                                         |
|  • 状态参数已完成 HMAC-SHA256 签名校验，但需注意重放攻击时间戳窗口。                    |
|                                                                                         |
| ┌─────────────────────────────────────────────────────────────────────────────────────┐ |
| │ ⚠️ 【系统安全熔断警示】                                                              │ |

| │ 为防止陷入死循环或算力浪费，系统已自动暂停后续自动响应。                           │ |
| │                                                                                     │ |
| │ [ 💬 输入补充指引继续推演 ]   [ ✅ 采纳当前方案并结束 ]   [ 🛑 终止并丢弃本次方案 ] │ |
| └─────────────────────────────────────────────────────────────────────────────────────┘ |
|                                                                                         |
|-----------------------------------------------------------------------------------------|
| ┌─────────────────────────────────────────────────────────────────────────────────────┐ |
| │ 输入指导意见，或点击“采纳方案”合流回主频道...                                       │ |
| └─────────────────────────────────────────────────────────────────────────────────────┘ |
|  [⚡ 注入引导 (Steering)]                                            [发送指引并唤醒 ➔] |
+-----------------------------------------------------------------------------------------+
```

### 5.2 状态转换与微交互细节
1. **静默状态感知**：当讨论完成且各 Agent 进入自然静默时，面板状态栏平稳切换为 `⚪ 讨论已收敛 (讨论完毕，等待人类决策)`，无闪烁与报错。
2. **熔断卡片吸底展示**：熔断卡片吸附在最后一条消息下方，高亮展示，并发出轻微柔和的系统提示音（可设置关闭）。
3. **一键终止二次确认**：点击“强制终止 (Abort)”时弹出轻量级确认框，防止误触导致未保存的设计草稿丢失。
4. **键盘快捷键**：
   - `Esc`：快速关闭侧边抽屉（不打断后台推演）；
   - `Cmd + Enter`：以当前选择的模式（Steer 或 Normal）快速发送消息；
   - `Cmd + Shift + X`：直接唤起“结束讨论并沉淀共识”弹窗。

## 6. 非功能性需求 (NFR)

1. **响应延时**：
   - Steering 注入指令在本地进程间通过 IPC/stdio 发送，端到端延迟 $< 20\text{ms}$；
   - 触发连续 8 轮熔断时，UI 警示卡片呈现延迟 $< 50\text{ms}$。
2. **算力与资源防耗**：
   - 熔断机制强制阻断后，所有与该 Thread 相关的 Agent 后台生成任务必须在 1 秒内平稳挂起或降级，严禁持续占用 CPU/GPU。
3. **数据一致性与审计**：
   - 无论讨论是通过静默完结、熔断挂起还是人工终止，完整的推演过程与 Steering 注入事件都必须以 Nostr 加密事件完整归档，支持事后完整回溯与回放。
