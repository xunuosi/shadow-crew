## 0. 一页纸决策摘要 (Executive Summary)

* **核心命题**：多个 Agent 自由讨论决策**并不会自发变得更准确**。相反，极易陷入从众附和、平庸折中、同质化偏见放大与“雄辩胜于事实”的伪共识黑洞。
* **设计主张**：高准确率决策不能依赖“自由辩论”，必须依靠**“受控的制度性博弈对抗与实证闭环”**。
* **六大核心机制**：
  1. **博弈对抗与反例质询（The Challenger）**：由挑战者强制寻找反例、边界失效场景与事前剖析（Pre-mortem），拒绝无意义抬杠；
  2. **角色三元组与人类仲裁（The Game Triad）**：设立“主导者 - 挑战者 - 中立仲裁者”，**仲裁者可配置为人类用户自身**，掌握终审法槌；
  3. **德尔菲盲审（Blind Review Phase）**：首轮全员互不可见、独立起草，根除先入为主的“首发发言锚定偏见”；
  4. **工具验真与举证责任（Tool Grounding & Burden of Proof）**：空对空辩论无效，主张必须附带代码执行、搜索或数据验真实证；
  5. **对齐 Shinobi 原生收敛与仲裁者特权截断**：严禁硬编码限制讨论轮数，依靠“局部信息价值自然静默 + 8 轮安全熔断”，**限定人类角色为仲裁者时可随时一键截断裁决**；
  6. **诚实暴露不确定性（Trade-off Matrix）**：不可调和分歧不强求和稀泥，直接输出《决策权衡矩阵》交人类拍板。

## 1. 核心背景与问题剖析

### 1.1 痛点诊断：为什么单纯多 Agent 讨论不等于更高准确率？

在当前以大语言模型（LLM）为底座的多 Agent 系统中，若仅给予各 Agent 一个身份并将其置于自由发言的聊天室内，通常会迅速遭遇以下五大退化陷阱：

| 现象名称 | 机理描述 | 对最终决策的破坏性后果 |
| :--- | :--- | :--- |
| **从众与谄媚偏见 (Herding & Sycophancy)** | 模型天生倾向于顺应前文上文与主流基调，讨好首发观点。 | 第一个发言者的微小偏差在后续发言中被不断附和、层层加固，形成伪共识。 |
| **首发锚定效应 (Anchoring Bias)** | 后续 Agent 在思考时，注意力机制（Attention）被首位发言者的框架严重锁定。 | 讨论始终在预设窄道内打转，丧失了探索全局最优解的可能性。 |
| **平庸折中陷阱 (Golden Mean Fallacy)** | 当发生实质分歧时，LLM 倾向于扮演“理中客”，各打五十大板求和。 | 妥协出的混合方案既丢失了方案 A 的极致性能，又未解决方案 B 指出的安全性隐患。 |
| **同质化认知盲区 (Homogeneous Bias)** | 参与讨论的 Agent 若基于同一基座模型，其知识切片和推理缺陷高度重合。 | “三个臭皮匠”本质上是“同一个大脑分身自言自语”，盲区未被消除，反而因互相印证而产生虚假高置信度。 |
| **雄辩胜过事实 (Rhetoric Over Truth)** | 格式优美、长篇大论、逻辑修辞严密的回复往往更容易在下轮被模型采信。 | 只要表达足够自信，虚假事实与臆造数据即可轻易击败简短但真实的警告。 |

### 1.2 产品设计原则 (Core Principles)

针对上述系统性失效，Shinobi 确立了多 Agent 决策治理的五大基本法则：

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   Shinobi 高准确率决策治理基本法则                     │
├────────────────────────────────────────────────────────────────────────┤
│  1. 独立思考先于相互影响 (Independence Before Interaction)             │
│  2. 理性博弈优于表面和谐 (Constructive Game-Debate Over Fake Harmony) │
│  3. 事实举证高于修辞辩才 (Empirical Evidence Over Rhetoric)             │
│  4. 规则量化多于主观投票 (Rubric Scoring Over Subjective Voting)       │
│  5. 暴露权衡胜于虚假共识 (Transparent Trade-offs Over Forced Consensus)│
└────────────────────────────────────────────────────────────────────────┘
```

## 2. 核心系统功能架构与模块设计

为了让多 Agent 协同讨论的结论真实逼近最优解，Shinobi 在现有的 `Topic Thread`（议题讨论面板）之上构建专门的 **“博弈讨论模式 (Game-Theoretic Discussion Mode)”**。

```text
               [用户发起博弈讨论模式议题]
                 (预设主导者、挑战者与仲裁者)
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
    [阶段一：德尔菲盲审]              [阶段一：德尔菲盲审]
     主导者: 方案起草                 挑战者: 预备攻击点
     (独立思考，互不可见)              (独立思考，互不可见)
            └────────────────┬────────────────┘
                             │ (全员提交后揭盲)
                             ▼
    [阶段二：方案博弈与反例质询 (The Challenger)]
     • 挑战者专门寻找脆弱假设、单点故障与失效边界
     • 提出极端工况反例与事前剖析 (Pre-mortem)
     • 主导者提供代码防御与补丁抗辩
                             │
                             ▼
    [阶段三：实证接地与工具验真 (Empirical Grounding)]
     • 调用 REPL 执行代码 / 压测模拟 / 数据库检索
     • 任何关键主张必须附带执行凭证 (Burden of Proof)
                             │
                             ▼
    [阶段四：收敛与仲裁裁定 (Arbitration)]
     • 局部信息价值无增量时自然静默收敛
     • 或由【中立仲裁者】(人类自己或 System-Arbiter) 执行终审
                             │
             ┌───────────────┴───────────────┐
             ▼                               ▼
    [达成明确最优解]                 [存在不可调和取舍]
    输出：决策方案 + 风险清单         输出：《决策权衡矩阵》
             └───────────────┬───────────────┘
                             ▼
              [阶段五：仲裁者敲锤定稿归档]
```

### 2.1 模块一：方案博弈与反例质询机制 (Boundary Challenge & Pre-mortem)

在博弈讨论模式中，系统引入专门持有反向质询视角的 Agent（在 Shinobi 中命名为 **`Challenger (边界挑战者 / 方案压测员)`**）。

#### 1. 角色职责与边界定义
* **不是无理取闹的“杠精”**：严格禁止在公认常识或客观事实（如数学计算、已知标准库行为）上进行无意义的纠缠；
* **定位为“极端工况压测与反例提供者”**：
  - **攻击隐藏假设**：“如果网络延迟从 5ms 突增到 2s，你的缓存一致性还会成立吗？”
  - **实施事前剖析 (Pre-mortem)**：“假定这个方案上线半年后导致了重大事故，最可能因为哪个未被验证的边界条件引发？”
  - **寻找非对称风险与过度设计**：“该方案带来的 10% 性能提升，是否承受了全库死锁的尾部风险？或者引入了不必要的分布式复杂度？”

#### 2. 挑战者发言规范契约 (Contract)
挑战者 Agent 发言必须强制遵循固定的四段论结构，否则视为无效发言并由系统拦截重试：
1. **被质疑的靶点声明**：明确引用主导者方案中的具体论点、状态流转或代码片段；
2. **失效场景构造 (Failure Scenario)**：提供具体的输入数据、高并发场景或极端故障环境变量；
3. **推演连锁反应**：阐明系统在此场景下为何崩溃、数据如何失真；
4. **防御检验要求**：要求主导者提供补丁防御设计、降级兜底方案或实证测试数据。

---

### 2.2 模块二：德尔菲盲审机制 (Delphi Blind Review)

#### 1. 业务逻辑
* 当议题开启“博弈讨论模式”后，第一轮讨论为 **严格独立盲审（Blind Phase）**；
* 受邀的主导者与挑战者 Agent 各自收到初始 Context 与议题描述；
* **视线隔离**：在所有 Agent 完成方案提交前，任何一方均无法读取对方的中间草稿或初步思路；
* **揭盲机制（Reveal）**：
  - 触发条件：所有受邀成员均已提交首轮独立方案，或者触及盲审超时阈值；
  - 揭盲后，系统自动生成“观点聚类与分歧总览”，将各方方案并行推入时间线，正式开启点对点博弈质询。

#### 2. 收益
从根本上切断“谁手速快、谁先发言就带节奏”的锚定偏见，保护初始思考的多样性与独立探索能力。

### 2.3 模块三：博弈角色三元组与预设体系 (The Game-Theoretic Triad & Presets)

系统放弃割裂的多角色堆叠，收敛为经典的**“主导 - 挑战 - 仲裁”黄金三元博弈模型**：

```text
┌────────────────────────────────────────────────────────────────────────┐
│                      Shinobi 博弈三元组架构                            │
│                                                                        │
│   ┌───────────────────────┐            ┌───────────────────────────┐   │
│   │ 主导者 (Proposer)     │ ◄── 博弈 ──► │ 挑战者 (Challenger)       │   │
│   │ 方案提出、答辩、补丁防御│     质询   │ 漏洞攻击、反例压测、成本挑刺│   │
│   └───────────┬───────────┘            └─────────────┬─────────────┘   │
│               │                                      │                 │
│               └──────────────────┬───────────────────┘                 │
│                                  ▼                                     │
│                     ┌───────────────────────────┐                      │
│                     │ 中立仲裁者 (Arbiter)      │                      │
│                     │ 👤 人类自己 或 🤖 系统裁判 │                      │
│                     │ 持有最终裁决法槌，定稿归档│                      │
│                     └───────────────────────────┘                      │
└────────────────────────────────────────────────────────────────────────┘
```

#### 1. 三元角色职责分工
1. **主导者 (`@Proposer`)**：方案的“主提出方”。负责提出核心架构草案、模块边界与 API 定义；面对质询时负责编写补丁防御或提交实证代码。
2. **挑战者 (`@Challenger`)**：方案的“压力测试员”。专门负责寻找隐含漏洞与边界失效，同时负责审查成本与过度设计（*替代了冗余的极简角色，将极简与成本自然作为挑战者的攻击切面*）。
3. **中立仲裁者 (`@Arbiter`)**：不参与双方细节论战，居中掌握评定与终审拍板权。
   - **支持配置为“👤 我自己”（人类开发者）**：人类亲自作为仲裁者坐镇，在后台观摩双方攻防，随时行使最终法槌裁决权；
   - **支持配置为“🤖 系统裁判”（`@System-Arbiter`）**：在离线或无人值守场景下，由系统 Meta-Agent 依据显式量化量表出具裁决报告。

#### 2. 预设与快速选择机制 (Presets & UX Flow)
* **创建议题弹窗预设**：用户勾选“博弈讨论模式”时，系统提供一键角色匹配，无需手动逐个填写；
* **特长自动映射**：系统根据频道成员标签（如带有 `Security` / `Audit` 倾向）自动建议挑战者，主导者默认指派给核心业务 Agent；
* **仲裁者默认偏好**：系统默认推荐“👤 我自己 (持有最终裁决权)”，保证人类开发者牢牢掌握技术拍板权。

### 2.4 模块四：实证接地与工具验真机制 (Tool Grounding & Burden of Proof)

纯靠自然语言互相对攻，模型容易产生“幻觉对幻觉”的螺旋式错误。系统引入**“举证责任制度”**：

1. **事实性断言判定**：
   - 当 Agent 在发言中做出性能提升、并发安全、库函数行为、复杂度等硬性断言时，系统标记该断言为待验真状态；
2. **工具赋权支持**：
   - **代码沙盒执行器 (REPL Sandbox)**：Agent 可编写微型测试用例，真实运行并捕获吞吐、内存及 Panic 日志；
   - **实时检索器 (Web/Knowledge Search)**：检索官方技术文档、GitHub Issue、RFC 规范；
   - **数据库/日志探测器**：在沙盒环境中查询真实样本数据；
3. **无凭证据惩罚**：
   - 仲裁系统判定论据权重时，**包含执行结果/真实日志引用的权重为 1.0，纯文本陈述的权重仅为 0.2**。

### 2.5 模块五：中立仲裁裁判与人类裁决法槌 (Arbiter & Human Decision Gavel)

为了避免 Agent 讨论退化为无休止的争吵，或和稀泥式的无原则折中，系统设立**中立仲裁者（Arbiter）**机制。

#### 1. 仲裁者双模态运行
* **模态 A：人类亲自仲裁（Human as Arbiter - 默认推荐）**：
  - 议题将人类开发者本身标记为 `Arbiter`；
  - 两位 Agent（主导者与挑战者）在台前展开攻防，人类拥有专属的**【仲裁法槌控制台】**，随时根据直觉或量表直接敲锤定音。
* **模态 B：系统 Meta-Agent 托管（AI as Arbiter）**：
  - 由 `@System-Arbiter` 依据客观量化量表出具结构化评定报告。

#### 2. Rubric 量化评价维度表 (总分 100 分)

| 评分维度 | 权重 | 评估细则与扣分点 |
| :--- | :---: | :--- |
| **实证支撑度 (Evidence Grounding)** | **35%** | • 是否附带代码运行、官方规范、基准测试凭据？<br>• 若仅为主观猜想或缺乏依据的断言，扣 20 分。 |
| **反脆弱与边界防御 (Robustness)** | **25%** | • 是否成功防住了挑战者指出的极端工况与失效场景？<br>• 是否提供了降级与兜底设计？ |
| **逻辑推导闭环 (Logical Rigor)** | **20%** | • 从前提、论据到结论是否存在逻辑跳跃或自相矛盾？ |
| **实现代价与极简度 (Cost & Simplicity)** | **20%** | • 是否存在严重过度设计？在满足安全前提下工程成本是否合理？ |

#### 3. 产出报告格式
仲裁最终输出《决议通报》，包含：
* **胜出方案与核心采纳理由**；
* **被采纳方案中仍需修复的缺陷清单（吸收自挑战者意见）**；
* **被否决方案的致命缺陷审计**。

### 2.6 模块六：诚实暴露不确定性——《决策权衡矩阵》 (Trade-off Matrix)

真实技术世界中，并非所有议题都有全局最优解（例如 CAP 定理中的一致性与可用性权衡）。

* **触发机制**：当挑战者提出的攻击场景在物理上与原方案的优势不可兼得，且两方得分极其接近时，仲裁者 **禁止强制合成一个毫无特色的平庸方案**；
* **输出成果**：自动生成《客观权衡矩阵 (Trade-off Matrix)》，明确列出分歧点：
  - **选项 A（高性能偏向）**：牺牲严格一致性，适合非资金类流媒体业务，面临风险点为极端场景轻微脏读；
  - **选项 B（强一致性偏向）**：引入分布式两阶段提交，增加 40ms 延迟与 50% 架构复杂度，但保证零资损；
* **交由人类决策**：卡片直接将选择题抛回给人类开发者，人类勾选即完成议题归档。

### 2.7 模块七：底层模型异构与参数多样性 (Heterogeneous Config)

消除模型单点共性盲区：
1. **模型异构分配**：
   - 提案主导者（`@Proposer`）：挂载擅长系统代码生成与逻辑发散的推理模型（如 Claude 3.7 Sonnet / Gemini 1.5 Pro）；
   - 边界挑战者（`@Challenger`）：挂载擅长深度逻辑审校与安全审计的批判型模型；
   - 仲裁裁判者（`@Arbiter`）：挂载长上下文、高遵循度、严谨评分模型；
2. **采样参数分化**：
   - 主导者与挑战者角色的 Temperature 设为 `0.7`（激发反例构造与多样性方案）；
   - 仲裁与验真执行角色的 Temperature 强制锁定为 `0.1`（追求绝对严谨与确定性）。

## 3. 讨论治理工作流与原生收敛机制

博弈讨论模式**严禁使用硬编码指定轮数（如强制第 2 轮结束）的机械做法**，而是完全对齐 Shinobi 原生的三层收敛与治理机制：

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   Shinobi 博弈讨论三层收敛闭环                          │
│                                                                        │
│   [顶层特权] 机制三：人类仲裁者专属法槌随时截断 (Arbiter's Gavel)        │
│       ▲       • 仅限定人类角色为【仲裁者】时可见并执行                 │
│       │       • 随时敲锤：采纳主导方案 / 采纳挑战重构 / 生成权衡矩阵   │
│       │                                                                │
│   [系统兜底] 机制二：连续 8 轮未介入安全熔断 (Circuit Breaker)         │
│       ▲       • 双方攻防连续 8 轮无人类介入时自动刹车挂起              │
│       │       • 冻结自动事件，插入警示卡片，等待仲裁者处理             │
│       │                                                                │
│   [底层自主] 机制一：局部信息价值自然静默收敛 (Silence as Completion)   │
│               • 主导者补齐防御且挑战者无新增反例时，自主保持静默       │
│               • 消息总线无新增事件，讨论自然平稳收敛                   │
└────────────────────────────────────────────────────────────────────────┘
```

### 3.1 状态机流转

```text
[State: DRAFT]
  │ (用户在弹窗预设三元角色并点火)
  ▼
[State: DELPHI_BLIND] ──(所有成员完成起草 / 超时)──► [State: UNMASKED]
                                                              │
                                                              ▼
                                                     [State: GAME_DEBATE]
                                                     (挑战者反例质询 + 主导者防御抗辩)
                                                              │
                                                              ├──► [触碰自然静默] ──► 自动收敛
                                                              ├──► [触碰 8 轮熔断] ──► 挂起等待仲裁
                                                              └──► [人类仲裁者敲锤] ─┐
                                                                                     ▼
                                                                            [State: RESOLVED]
                                                                            (输出结论与权衡矩阵)
```

### 3.2 详细收敛逻辑说明

1. **机制一：局部信息价值自然静默（底层平稳收敛）**
   - 挑战者提出反例场景 $\to$ 主导者补充代码防御或幂等设计；
   - 挑战者在本地评估：主导者的新代码是否已完全防御该场景？自身是否还能找出新的**严重级别**边界反例？
   - 若防御成立且无新反例，挑战者发言 *“✅ 已验证防御闭环，无新增致命反例”* 并**主动保持静默**；
   - 双方均无新增量信息，讨论自然收敛。
2. **机制二：连续 8 轮无干预安全熔断（中间防死锁兜底）**
   - 若双方在微小逻辑上僵持不下、连续交互达到 **8 轮** 且中途无人类发言，系统内置的 **Circuit Breaker** 立即生效，冻结自动事件，等待仲裁裁决。
3. **机制三：人类仲裁者专属法槌截断（顶层绝对拍板权）**
   - **权限限定原则**：**只有在议题中被配置为【中立仲裁者 (Arbiter)】的人类用户**，界面底部才会激活【仲裁法槌】操作栏；
   - 普通观察员人类成员仅有发言权，无权随意掐断博弈进程；
   - 人类仲裁者在任何轮次均可随时一键截断：
     - **`[ ⚖️ 采纳主导方案 ]`**：认定方案可行，忽略轻微反例，直接归档；
     - **`[ ⚖️ 采纳挑战意见 ]`**：认定漏洞致命，要求主导者推翻重构；
     - **`[ ⚖️ 生成权衡矩阵 ]`**：认定分歧属于固有取舍，生成矩阵并交由业务定夺。

## 5. 非功能性需求 (NFR)

1. **真实性与偏见抑制指标**：
   - 在启用博弈讨论模式下，盲审重合度监测：若主导者与挑战者输出语义相似度 $> 0.95$ 且未提出任何反例，触发异构重试警告；
   - 虚假共识率降低目标：在对抗实验集下，重大隐性设计缺陷被挑战拦截率 $\ge 85\%$。
2. **算力与 Token 预算保护**：
   - 对齐既有治理框架，受连续 8 轮无人类干预熔断硬保护；
   - 整体博弈决策流程的 Token 消耗上限可配置（默认单议题硬上限 $\le 60,000$ Tokens），超出时强制截断并交付仲裁者。
3. **工具沙盒安全 (Execution Safety)**：
   - 验真 Agent 调用 REPL 运行的代码必须运行在受限 Docker / WASM 沙盒中；
   - 严禁对生产网络或不可逆存储执行破坏性测试（只读或本地 Mock）。
4. **决策审计可回溯性**：
   - 所有的独立草案（即使后续被推翻）、反例攻击用例、测试脚本、仲裁裁决理由，均需完整打包记录进议题的 Nostr 状态链中，具备不可篡改与全流程审计能力。
